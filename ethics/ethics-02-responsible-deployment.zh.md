# 負責任部署：把模型放上線前後，該做的每一件事

> 📅 2026-08-04 · 使用教學
> 示範裡的模型總是完美，真實世界不會照劇本走。負責任部署是把『評估、護欄、測試、監控、人審、下架』變成一套工程習慣——風險越高，防護越厚。

---

示範影片裡，模型完美回答了每個問題，會議室響起掌聲。然後你把它放上線——真實世界的使用者不會照著劇本問問題。有人繞過限制、有人故意挑釁、有人把你的答案當成專業意見照單全收。

這篇不是「AI 很危險所以要小心」的喊話，而是一套具體的工程流程：**上線前要評估什麼、上線時要裝什麼護欄、上線後要盯什麼指標、以及哪天要怎麼把它收掉。**

## 能力與傷害：同一顆引擎的兩面

第一步是誠實評估「這個功能最糟會出什麼事」。能力越強、越靠近「影響真實決策」的地方，錯誤的帳單就越貴。先分風險等級，再決定投入多少防護：

| 使用情境 | 錯誤的後果 | 需要的防護 |
|---|---|---|
| 草稿一封電子郵件 | 低——改一改就好 | 輕量護欄 |
| 客服摘要 | 中——可能誤導 | 人工抽檢 |
| 審核貸款 / 篩選履歷 | 高——影響人生 | 人類做決定、審計軌跡 |
| 醫療或法律建議 | 極高——不可逆 | 專業審查、強制邊界、法規遵循 |

關鍵不是「禁止高風險用途」，而是「**風險越高，防護越厚**」。同一顆模型，放在寫 email 和放在看病上，需要完全不同的工程投入。也別忘了：你的產品目標，可能跟「使用者的最佳利益」有落差——例如一個誘導使用者多付費的購物助理，模型「正確地完成任務」，對使用者卻是有害的。

## 失敗模式：先列出來，再防

風險評估最有效的做法，是先列出這個功能的**失敗模式**——每一種「出錯」的具體長相，然後逐一問「這條路走得通嗎」：

| 失敗模式 | 例子 | 對策 |
|---|---|---|
| 幻覺當事實 | 模型把編造的引用、數字當真 | 引用檢查、限制輸出範圍（見 `llmcore-05-hallucination`） |
| 誤導高風險決定 | 醫療、法律、金融建議出錯 | 硬攔截、轉人工 |
| 被濫用 | 用客服機器人套取個資 | 輸入端過濾、敏感資訊偵測 |
| 悄悄劣化 | 新資料上線後品質下滑 | 監控錯誤率、設自動回滾 |

列失敗模式的目的不是窮盡所有可能，而是**把「風險」從模糊的擔憂，變成可以逐條打勾的檢查項。** 寫不出失敗模式的功能，往往正是還沒想清楚的功能。

## 免責聲明不是護欄

「本回答由 AI 生成，可能包含錯誤」——這句話很好，但它是**免責聲明**，不是**護欄**。免責聲明管理期望；護欄改變行為。

`security-06-guardrails` 已經給過完整的多層防禦：輸入端過濾、系統提示護欄、不可信內容隔離、輸出端硬檢查。倫理風險用同一套思路：**假設模型會犯錯，然後在輸出碰觸真實世界之前，放一道不依賴模型自律的檢查。**

```python
def guard_high_stakes(raw: str) -> str:
  if "確診" in raw or "投資建議" in raw:
      raise PermissionError("高風險領域，改為引導人工諮詢")
  if not re.search(r"我無法確認", raw):
      return raw
  return raw
```

輸出端的硬檢查不是萬靈丹，但它保證「最糟的那條路走不通」。

> 護欄與免責聲明要分開看：免責聲明告訴使用者「要小心」，護欄保證系統「出不了大事」。 高風險功能需要的不是更漂亮的免責文字，而是更硬的檢查——如果你只能做一件事，先做輸出端的那一道。

## 上線前：測的不只是「準不準」

測試的重點不是「模型在測試集上拿多少分」，而是「**在不同人群、不同邊緣輸入下，會不會出事**」：

1. **定義任務與失敗**：「正確」長什麼樣？「不可接受」長什麼樣？先寫清楚。
2. **建立評估集**：涵蓋不同方言、不同表達方式、邊緣案例——不要只涵蓋「看起來像使用者會問的」。
3. **紅隊壓力測試**：主動找「會誘發錯誤或濫用」的輸入（`security-06-guardrails` 的紅隊精神）。
4. **小範圍試跑**：灰度發布、限制流量、觀察真實資料，再逐步放大。

測試的對象不只是模型，還有你的提示詞、你的介面、你的護欄——**整個產品是系統，模型只是其中一環。** 一個在「乾淨的示範題」上滿分的模型，遇到真實世界的雜訊輸入，表現可能完全不同。

## 上線後：監控與事故回應

模型上線不是終點，是起點：

| 指標 | 看什麼 |
|---|---|
| 錯誤率 / 投訴率 | 有沒有劣化、有沒有系統性偏差 |
| 不同族群的成功率差異 | 偏見有沒有在真實流量裡重現 |
| 回饋迴路 | 使用者回饋有沒有被拿去訓練、有沒有被灌毒 |
| 攔截率異常 | 護欄有沒有失效 |

另外準備一份**事故回應計畫**：誰負責判定、多久內回應、最糟情況怎麼把功能關掉。沒有計畫的事故應對，就是在最忙的時候邊學邊做。

## 高風險場景：人做決定，不是蓋章

對貸款、醫療、法律這類「影響人生」的決策，人類審查不是選配：

* **人做最終決定**：模型給建議，人做判斷。不要讓「不可逆」的決策自動化。
* **審查不能變蓋章**：人有「自動化偏誤」——傾向相信機器的輸出。要設計「允許質疑」的流程，甚至刻意讓人不時看到「AI 也會錯」的證據。
* **留審計軌跡**：每個決定都能事後回溯——「模型建議了什麼、人類決定瞭什麼」。

```text
使用者 → [模型建議] → [人工審查] → 最終決定
↑
審計軌跡：留下雙方紀錄
```

## 一個貫穿的例子：客服助理

把整條流程套在一個具體功能上。假設你要上線「客服助理」，負責回覆使用者關於退款的問題：

1. **風險評估**：誤導使用者退錯款是中高風險，決定「高金額退款一律轉人工」。
2. **評估集**：涵蓋生氣的使用者、錯字、方言，以及「想騙系統多退款」的惡意輸入。
3. **護欄**：輸出端硬檢查——「退款金額超過門檻」時，強制回覆「需要人工核對」（`security-06-guardrails`）。
4. **試跑**：先讓 5% 流量使用兩週，觀察錯誤率與投訴率。
5. **監控**：追蹤「高金額誤導」事件數與族群差異；一出事先跑事故流程。
6. **下架**：若合規要求改變，能一週內關閉並匯出對話紀錄。

一個功能不是「上線」或「沒上線」，而是**在每一站都有明確決策的系統**。

## 下架也是一種責任

很少有人談，但「把功能收掉」也是部署的一部分。哪天模型劣化、成本失控、或法規改變，你要能**乾淨地退出**：提前公告、給使用者匯出或替代方案、刪除用過的資料、留下評估紀錄。一個「隨時可以收掉」的功能，才是一個「敢放心上線」的功能。

## 一份實用檢查清單

把前面的步驟壓成一份可以直接對照的清單：

#### 界定用途與風險

寫下「要解決什麼」與「最糟會出什麼事」，分出風險等級。

#### 建評估集

覆蓋不同人群與邊緣案例，定義「可接受」與「不可接受」。

#### 裝護欄

依風險等級裝上輸入與輸出端的硬檢查（`security-06-guardrails`）。

#### 小範圍試跑

灰度發布，觀察真實流量與錯誤率，再放大。

#### 上線監控

盯錯誤率、族群差異、攔截率，設事故回應流程。

#### 高風險交人

不可逆的決策由人做最終判斷，留審計軌跡。

#### 準備下架

寫好退出計畫：公告、匯出、刪資料。

## 下一步

把模型放上線，是「讓 AI 影響真實世界」的時刻。但比「模型會做錯」更讓社會頭痛的是另一件事：**有人用 AI 刻意製造假的真實**——深偽與資訊操縱，`ethics-03-deepfakes`。

#### Q: 為什麼「本回答由 AI 生成，可能包含錯誤」這句話不算是護欄？

* 因為它是免責聲明，管理的是期望；護欄改變的是行為

* 因為使用者根本不會讀這句話

* 因為這句話會拖慢模型回應速度

* 因為只有中文版本有效，英文版本無效

> 💡 免責聲明告訴使用者「要小心」，但沒有改變模型的行為；護欄則是在輸入或輸出端放上不依賴模型自律的硬檢查。兩者目的不同，不能互相取代。
