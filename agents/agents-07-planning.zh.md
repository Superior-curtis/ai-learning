# 規劃與子代理：把任務拆開，讓工作平行

> 📅 2026-08-04 · 深入研究
> 規劃是 Agent 的導航系統：從拆解任務、決定順序，到派子代理平行作業，並了解何時規劃反而幫倒忙。

---

## 開場：一個任務，兩種做法

「寫一份關於 2026 年 AI 市場的報告。」如果直接丟給一個沒有規劃能力的 Agent，它會從第一個字開始苦幹，邊寫邊查，寫到一半發現前面的段落資料過時，只好回頭重寫——像沒看地圖就上路。

如果讓它先規劃，一切不同：先列出需要的資料、分派「誰去查哪塊」、決定撰寫順序、最後再審查。同樣的任務，成本更低、品質更穩。**規劃，就是 Agent 的導航系統。**

***

## 規劃在做什麼

規劃是把一個大目標，拆成可執行的步驟。拆解的過程有三個層次：

| 層次 | 回答的問題 | 例子 |
|------|-----------|------|
| 目標 | 最終要達成什麼 | 寫一份 2026 市場報告 |
| 步驟 | 需要哪幾個階段 | 查資料 → 擬大綱 → 撰寫 → 審查 |
| 順序 | 先做哪個、哪些可平行 | 資料查詢可平行，撰寫需等資料 |

> 規劃的本質是延遲決定：先不寫第一段，而是先把「整件事該怎麼走」想清楚，再動手。想的時間不是浪費，是省下返工。

模型的「規劃能力」來自哪裡？回想 `llmcore-01-next-token`——模型在預測下一個 token 時，其實也在預測「整段回答最合理的走向」。給它明確的任務與工具，它可以先生成一份步驟清單，再逐步執行。

***

## Planner-Executor：最經典的規劃模式

把「規劃」和「執行」分給兩個角色，是 Agent 系統最常見的架構：

* **Planner（規劃者）**：負責想，產生一份步驟清單（plan）。
* **Executor（執行者）**：負責做，依序執行每個步驟，把結果回報。

```text
使用者需求
│
▼
Planner → 產出 plan：步驟 1、2、3 …
│                     │
▼                     ▼
Executor 執行步驟 1   Executor 執行步驟 2  ← 平行
│                     │
└──────────┬──────────┘
▼
彙整結果 → 回報使用者
```

為什麼要拆成兩個角色？因為「想」和「做」的最佳化方向不同：規劃者需要全局視野，執行者需要專注當下。分開之後，規劃者可以邊執行邊修訂計畫，執行者不用分心「下一步該做什麼」。

## 用子代理平行作業

規劃的第二步是派活。`agents-02-orchestration` 已經談過多代理編排，這裡聚焦一個關鍵決策：**什麼時候該派子代理平行作業？**

### 適合平行的三種情況

* **工作真正獨立**：例如查五家公司的財報，彼此毫不相干。
* **角色分工明確**：研究、撰寫、審查各司其職。
* **主代理上下文吃緊**：把部分工作外包，省下主代理的 token。

### 不適合平行的三種情況

* **步驟有依賴**：撰寫必須等資料齊全，硬拆只是白等。
* **共享狀態很多**：子代理各自做決定，最後矛盾無法收斂。
* **單一步驟很小**：派子代理的重啟成本，比自己做還貴。

```text
好的拆法：查 A、查 B、查 C → 三個子代理同時跑 → 彙整
壞的拆法：寫第一段 → 子代理寫第二段 → 子代理寫第三段（段落彼此需要連貫，拆了更難寫）
```

> 子代理不是加速器，是開銷：每次派發都要重新建立上下文、回報、再被主代理讀取。只有平行化的收益超過開銷時，才值得拆。

***

## 一個完整的規劃範例

假設任務是「做一份企業簡報」。規劃者會這樣拆：

```text
規劃：
  1. 平行：研究公司背景 / 收集市場數據 / 整理競品對照
  2. 依序：根據資料擬大綱 → 撰寫內文 → 審查與潤飾
  3. 收尾：產生最終簡報檔
```

執行時，第一步的三個研究子代理同時啟動；等三份資料都回報，才進入第二步的撰寫。這就是「先平行、後依序」的混合策略——也是絕大多數真實 Agent 應用的形狀。

```json
{
"goal": "做一份企業簡報",
"steps": [
  { "id": 1, "task": "研究公司背景", "depends_on": [] },
  { "id": 2, "task": "收集市場數據", "depends_on": [] },
  { "id": 3, "task": "整理競品對照", "depends_on": [] },
  { "id": 4, "task": "擬大綱",        "depends_on": [1, 2, 3] },
  { "id": 5, "task": "撰寫內文",      "depends_on": [4] }
]
}
```

把計畫寫成資料，最大的好處是**可以排序**：`depends_on` 空白的步驟（1、2、3）沒有依賴，就是平行的候選；有依賴的步驟（4、5）必須等前面的完成。Planner 產生計畫，調度器根據依賴排序派活——這套邏輯，正是多數 Agent 框架「任務圖」的雛形。

***

## 什麼時候規劃反而幫倒忙

規劃不是萬靈丹。三種情況，規劃反而有害：

### 1. 任務太簡單

「把這句英文翻成中文。」規劃只會增加延遲。**規劃有成本**——每次規劃都是額外的 token 與時間。

### 2. 環境變化太快

規劃假設「未來可以預測」。如果執行到一半需求就變了，嚴格的計畫會僵化，不如邊做邊調整。

### 3. 規劃本身不可靠

如果模型對任務領域不熟，它產生的步驟清單可能根本是錯的——一個錯的計畫，比沒有計畫更糟，因為它給了虛假的安全感。

判斷標準一句話：**可預測的複雜任務要規劃，簡單任務要直接做，快速變化的任務要邊做邊改。**

## 下一步

規劃讓 Agent 想清楚「該做什麼」，但計畫再好，執行時仍會出錯：子代理跑進死迴圈、工具選錯、上下文爆炸。下一篇 `agents-08-reliability` 談代理的可靠性與偵錯——失敗模式、護欄與預算、以及怎麼重試與驗證。會想、會做，還要會**在出錯時站穩**。

***

## 重點回顧

* 規劃 = 把大目標拆成步驟，三層次：目標、步驟、順序。
* Planner-Executor 把「想」與「做」分開，是經典架構。
* 子代理是開銷，只有平行化收益超過開銷才值得拆。
* 好的策略是「先平行、後依序」的混合。
* 規劃會幫倒忙的三種情況：任務太簡單、環境變化太快、規劃本身不可靠。

#### Q: 什麼情況下不該派子代理平行作業？

* 工作內容彼此完全獨立時

* 步驟之間有依賴、需要前一階段的結果時

* 需要研究多個獨立的資料來源時

* 主代理的上下文快要滿的時候

> 💡 有依賴的步驟無法真正平行——後續步驟必須等前面的結果，硬拆只會增加子代理的開銷而沒有收益；其餘三者（獨立工作、多來源研究、省上下文）正是適合派子代理的情況。
