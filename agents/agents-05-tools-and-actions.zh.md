# 工具與動作設計：Agent 如何對世界動手

> 📅 2026-08-04 · 核心機制
> 工具是 Agent 的雙手：從工具 Schema、動作分類，到錯誤處理與優雅失敗，完整拆解 Agent 怎麼真正「動手做事」。

---

## 一句話回顧：Agent 的迴圈裡，工具是「動手」的那一步

在本系列第一篇，我們把 Agent 拆成「模型 + 工具 + 迴圈」；在上一篇，你已經用 `get_weather` 和 `save_note` 寫出第一個會動的 Agent。但你注意到了嗎？迴圈裡真正改變世界的，只有一行：`run_tool(name, args)`。

這篇文章把這一行的裡裡外外講清楚——**工具長什麼樣、動作有哪些分類、失敗了該怎麼優雅地收場**。懂了這些，你寫的不是「會呼叫 API 的程式」，而是一個真的能對世界動手、而且動手壞了也知道怎麼收拾的 Agent。

***

## 工具 = 一份「人機契約」

每個工具本質上是一份契約，寫清楚「什麼時候能用、要帶什麼參數、做完回傳什麼」。契約有三個欄位：

| 欄位 | 作用 | 為什麼重要 |
|------|------|-----------|
| `name` | 唯一識別碼，模型呼叫時指名道姓 | 名稱要準確：`get_weather` 一看就懂，`process_thing` 沒人懂 |
| `description` | 用自然語言說明用途與適用時機 | 模型靠它決定「這題該不該用這個工具」 |
| `input_schema` | JSON Schema 定義參數結構 | 讓模型知道該填什麼、哪些必填 |

> description 是整個契約裡最容易被忽略、卻最關鍵的一欄。工具再強，模型不知道什麼時候該用它，等於沒寫。

Schema 的學問叫 JSON Schema——它描述「參數是字串還是數字、要不要必填、可以有哪些取值」。模型拿到 Schema，就知道該生成什麼形狀的 `arguments`。

```json
{
"name": "get_weather",
"description": "查詢指定城市的目前天氣，回傳氣溫與天氣狀況。",
"input_schema": {
  "type": "object",
  "properties": {
    "city": { "type": "string", "description": "城市名稱，例如 台北" },
    "unit": { "type": "string", "enum": ["celsius", "fahrenheit"], "default": "celsius" }
  },
  "required": ["city"]
}
}
```

## 動作的四種基本型態

工具名目繁多，但動作大致落在四類。辨識你的工具屬於哪一類，有助於設計它的描述與錯誤處理。

### 1. Call：呼叫既有 API

把既有的服務包成工具——查訂單、寄信、建 issue。這是最常見的一類。

### 2. Search / Browse：查詢與瀏覽

在文件、網頁、資料庫裡找東西。重點是**結果可能是多筆或不完整**，模型需要自行判斷哪筆最相關。

### 3. Execute：執行程式與寫檔

執行指令、編輯檔案。這類工具權限最高，也最容易出意外——把「只能讀」和「可以寫」的權限分開，是基本的安全底線。

### 4. 混合型

例如「搜尋後回傳摘要」「讀檔後統計」——一次完成兩件事，減少來回次數。

> 判斷動作型態的捷徑：Call 問「有沒有」、Search 問「在哪裡」、Execute 問「改成怎樣」。問法不同，失敗時的處理也該不同。

## 動作的完整生命週期

一個工具呼叫從「模型想要動手」到「結果回到模型」，其實是一趟小旅程：

```text
模型決定呼叫 → 生成 arguments → 系統執行工具 → 取得結果
│
←── 結果進上下文 ── 成功或失敗都一樣 ──┘
```

* 模型從不「真的」執行程式碼——它只是**生成一段結構化的呼叫意圖**（tool use block）。
* 真正執行的是系統這側的程式，例如你的 `run_tool` 函式。
* 執行完，把結果包成 `tool_result` 回傳給模型，讓它繼續下一圈。

把「呼叫意圖」與「真正執行」分開，是 Agent 安全設計的關鍵：**模型只能提議，系統才能批准執行**。`agents-03-mcp` 的標準化介面，正是為了讓這個旅程的每一站都有一致格式。

## 失敗，是工具使用者的日常

真實世界沒有百分之百成功的工具。網路會斷、API 會回 500、檔案根本不存在。問題不是「會不會失敗」，而是「失敗之後模型知不知道」。

最常見的做法是回傳 `is_error: true`，讓模型清楚看到「這次動手壞了」：

```text
tool_result (is_error: true)
"訂單 API 回傳 404：找不到訂單編號 ORD-12345"
```

失敗訊息本身也有學問：

| 失敗類型 | 好的錯誤訊息 | 壞的錯誤訊息 |
|---------|-------------|-------------|
| 找不到資料 | 「找不到訂單，可能是編號錯誤」 | 「error」 |
| 參數錯誤 | 「city 不能為空，請提供城市名稱」 | 「Bad Request」 |
| 暫時性故障 | 「服務忙碌，請稍後重試」 | 「fail」 |

好的錯誤訊息告訴模型**接下來能做什麼**——重試、換參數、還是承認做不到。這正是「優雅失敗」（graceful failure）的意義：

> 一個 Agent 的可靠度，不取決於它的工具多麼完美，而取決於失敗時它是否誠實地告訴模型。假裝成功，是所有 Agent 災難的起點。

***

## 讓失敗變成可回復的：三種防線

### 第一道防線：系統層重試

Rate limit（429）或暫時性連線錯誤，交給系統自動重試——例如睡兩秒再打一次，不必打擾模型。

### 第二道防線：把失敗餵給模型

系統重試幾次仍失敗，就把 `is_error: true` 回傳，讓模型決定換參數、換工具、還是直接道歉收尾。

### 第三道防線：給出「預設退路」

部分工具失敗時可以先回退到一個保守結果。例如搜尋引擎掛了，就回傳「搜尋暫時不可用」而不回傳空白——空白容易被模型誤讀成「沒結果」。

***

## 動手前，先問三個設計問題

寫任何工具前，先回答這三個問題，能省下大量偵錯時間：

* **這個工具的輸入，模型一定填得出來嗎？** 填不出來就該簡化 Schema 或合併工具。
* **失敗時，模型該往哪走？** 錯誤訊息裡要暗示下一步。
* **這個工具值得存在嗎？** 如果三行程式碼就能取代它，就別多一層。

工具越少、越專一、描述越清楚，模型的動作就越可靠。把工具當成 API 來設計、把錯誤訊息當成對話來寫，你的 Agent 就不會是「會動的玩具」，而是「能完成任務的夥伴」。

## 重點回顧

* 工具 = name + description + input_schema，是一份人機契約。
* description 決定模型「何時」用工具，是最關鍵的一欄。
* 動作四型態：Call、Search/Browse、Execute、混合型，失敗處理各不同。
* 模型只「提議」呼叫，系統才「執行」——兩者分離是安全關鍵。
* 失敗要回傳 `is_error: true`，並給出「接下來能做什麼」的訊息。
* 三道防線：系統重試 → 餵給模型 → 預設退路。

#### Q: 工具描述（description）的主要作用是什麼？

* 定義工具回傳資料的格式

* 讓模型判斷「什麼時候該呼叫這個工具」

* 設定工具的呼叫權限

* 決定工具的執行速度

> 💡 description 用自然語言說明工具用途與適用時機，模型靠它決定何時該動手；回傳格式由實際執行決定，權限由系統設定，速度與描述無關。
