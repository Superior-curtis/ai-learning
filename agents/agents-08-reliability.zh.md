# 代理可靠性與偵錯：讓 Agent 在出錯時站穩

> 📅 2026-08-04 · 深入研究
> 面對死迴圈、死路、錯工具與上下文爆炸，用護欄、預算與追蹤把 Agent 拉回正軌，並學會怎麼重試與驗證。

---

## 開場：Agent 的「可靠」，不是「永遠成功」

你已經會寫 Agent（`agents-04-first-agent`），會設計工具（`agents-05`），會拆任務與派子代理（`agents-07`）。但真實世界不配合：程式會卡住、會繞圈、會誤入歧途。一個「可靠」的 Agent 不是永遠不犯錯，而是**犯錯時能被發現、被阻止、被糾正**。

這篇是最務實的一篇：Agent 最常死在哪裡、怎麼用護欄和預算把它救回來、以及如何追蹤它的一舉一動。把它想成「把你的 Agent 從懸崖邊拉回來的手冊」。

***

## 四大失敗模式

Agent 的失敗林林總總，但八成可歸結為四類。認得它們，才能對症下藥。

### 1. 死迴圈（Infinite Loop）

Agent 不停呼叫工具，結果一輪比一輪雷同，永遠停不下來。最常見：某次呼叫傳回了「部分成功」的結果，Agent 誤以為還沒完成，繼續重試。

```
→ call_api → result: "partial" → call_api → result: "partial" → …
```

### 2. 死路（Dead End）

Agent 發現自己走進一條走不通的路，但又沒有退路——工具呼叫了、失敗了、沒學會換策略，只能卡在原地或者把同樣的錯再犯一遍。

### 3. 錯工具（Wrong Tool）

Agent 選錯了工具或傳錯了參數。表面上看它在「努力」，實際上南轅北轍。這通常源於工具描述不清（`agents-05`）或上下文裡有誤導資訊。

### 4. 上下文爆炸（Context Bloat）

每個工具結果都被塞進上下文，幾十輪下來窗口爆滿。後果不只是慢和貴——`llmcore-03-context` 提過，上下文過長，模型的判斷品質會下滑。資訊太多，跟太少一樣危險。

> 四種失敗的共同根源是缺少停止機制。模型天生不會自己喊停——所以「停止」必須由系統負責。

***

## 護欄：給 Agent 裝上煞車

既然 Agent 不會自己停，就要由系統設計三層「煞車」。這三層合稱 **guardrails（護欄）**。

### 1. 步驟上限（Max Steps）

限制 Agent 最多呼叫幾次工具。到了上限還沒完成就強制停止。最樸素也最有效：一個永遠不會停的迴圈，一旦設了上限，最多再跑 N 輪。

### 2. 時間或成本預算（Budget）

限制「多少秒」或「多少 token」。跟步驟上限不同，預算看的是**總代價**——有的步驟貴、有的便宜。成本型預算能防止 Agent 在價值低的步驟上浪費 token。

### 3. 結果驗證（Validation）

在系統層檢查結果是否合理。例如：寫完檔之後確認檔案真的存在、狀態碼是 200、回傳的欄位符合 Schema。`agents-05` 談過工具回傳要誠實，這裡是再補一道「系統自己檢查」的確認線。

| 護欄 | 限制的是 | 何時觸發 |
|------|---------|---------|
| Max Steps | 工具呼叫次數 | 達上限即停止 |
| Budget | 時間或 token | 超預算即停止 |
| Validation | 結果品質 | 不符預期即重試或告警 |

## 追蹤：讓 Agent 可以被觀察

護欄阻止災難，**追蹤（tracing）**讓我們看懂災難是怎麼發生的。一個 Agent 跑完，你應該能看到它的完整足跡：

```text
step 1: user → "寫一份市場報告"
step 2: agent → 呼叫 research_firms（參數：AI, 2026）
step 3: tool → 回傳 5 筆結果
step 4: agent → 呼叫 search_notes（參數：過往報告）
...
step 9: agent → 停止（達到 max_steps）→ 回報「已完成初稿」
```

每一行都記下：**當時的決策、呼叫了什麼、結果如何、花費多少**。這些紀錄就是偵錯的第一手材料——下次 Agent 卡住，你不是猜，而是直接看它哪一步走偏了。

> 追蹤的三個必記欄位：時間戳、工具名稱與參數、回傳結果與狀態。追蹤的目的不是記錄，是讓「為什麼失敗」在偵錯時有跡可循。

記到日誌之外，最好也把決策「標註」出來（例如每次工具呼叫附上理由），讓事後能判斷：當時的選擇合不合理？

***

## 如何重試與驗證

偵錯找到原因後，重試不是「再跑一次」那麼簡單。好的重試有策略：

### 重試的策略

* **辨別錯誤類型**：暫時性錯誤（429、連線失敗）值得重試；邏輯性錯誤（參數錯了）重試只是重蹈覆轍。
* **改變參數再試**：每次重試略為改變（換關鍵字、換工具），而不是用一模一樣的輸入硬撞。
* **帶退避**：加一點隨機延遲（backoff），避免多個 Agent 同時撞同一個服務。

### 驗證的步驟

* **自我驗證**：讓 Agent 用自己的話總結「我完成了什麼、證據是什麼」。
* **交叉檢查**：拿結果去對照來源，檢查數字、日期、引用是否一致。
* **人工抽查**：對高風險任務，保留一個人來確認關鍵輸出。

```text
失敗 → 分類錯誤 → 可重試？ → 是：改參數 + 退避後重試 → 驗證結果
│
└── 否：停止 → 記錄 → 給出部分結果 + 誠實說明
```

## 把一切串起來：一次偵錯實例

假設你的 Agent 反覆停在「寫分析報告」這步。你的追蹤顯示：

1. 它呼叫 `search_web` 得到一篇 2025 年的舊文（`agents-06` 提過：過期資訊比沒資訊危險）。
2. 它把這篇舊文的結論當成現況寫進報告。
3. 寫完後 `validate_report` 檢查到「引用年份過舊」，觸發重試。
4. 重試時 Agent 換了查詢條件，拉到 2026 年的新資料，驗證通過。

從追蹤看出：問題出在「檢索時沒帶時間濾鏡」，不在撰寫邏輯。修正方案很清楚——給 `search_web` 加時間範圍參數，或在取回時要求新鮮度。**這就是由資料驅動的偵錯**。

## 下一步與收束

八年下來，本系列從「什麼是 Agent」走到「怎麼讓 Agent 可靠」。如果你只記一件事：**Agent 的價值不在於一氣呵成，而在於出錯時系統能發現、阻止並糾正**——護欄、預算、追蹤、重試，缺一不可。會設計工具、會記憶、會規劃，最後還要有這副「煞車」，你的 Agent 才算真正可以委以重任。

***

## 重點回顧

* 可靠 ≠ 永遠成功，而是犯錯時能被發現、阻止、糾正。
* 四大失敗模式：死迴圈、死路、錯工具、上下文爆炸。
* 護欄三件套：Max Steps、Budget、Validation——由系統負責喊停。
* 追蹤記錄「什麼決策、什麼呼叫、什麼結果、花多少」，是偵錯第一手材料。
* 重試要有策略：辨別錯誤類型、改參數、帶退避；驗證用自我驗證、交叉檢查、人工抽查。
* 用追蹤資料找出根因，而不是瞎猜。

#### Q: 為什麼光靠模型自己無法避免死迴圈？

* 因為模型不具備語言能力

* 因為模型天生不會自主喊停，停止機制必須由系統設計

* 因為工具會自動停止執行

* 因為上下文窗口會自動截斷

> 💡 模型在生成回應時不會主動判斷「該停了」——它只持續預測下一個 token。所以「停止」必須由系統透過護欄（如 Max Steps 與預算）來強制執行，而不是指望模型自律。
