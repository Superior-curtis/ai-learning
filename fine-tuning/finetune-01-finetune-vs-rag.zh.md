# 微調 vs RAG：怎麼選

> 📅 2026-08-04 · 核心概念
> 改行為 → 微調；改知識 → RAG。這篇文章給一套決策框架與一張「什麼時候誰贏」的決策表，還談兩者怎麼並用。

---

你手上有一個「幾乎很棒」的模型，只是有兩件事不對勁：它回覆的語氣不像你的品牌，而且它不知道你每個月都會更新的產品資料。你該微調還是上 RAG？這個問題把很多人卡住，因為大家把它當成「二選一」——其實它是兩個不同工具，改的是兩種不同東西。

`train-02-finetuning` 已經把微調講清楚：它是「改模型權重」。RAG 我們也在 `rag-01-what-is-rag` 鋪陳過：它是「每次把資料塞進上下文」。這裡不再重定義，只談一件事——**什麼時候用哪個**。

## 兩個工具改的是不同的東西

一句話抓住本質：

* **RAG** 改的是「每一次輸入」的內容。你不需要動模型，只要在建構提示時把檢索到的資料放進去。
* **微調** 改的是「模型本身的權重」。你讓模型終身學會某個模式，之後不再需要每次都餵。

把模型想成一個通才員工：

* **RAG** 是「你每次交代工作時，順手遞給他一份最新資料」。
* **微調** 是「你把他送去上專業訓練班，讓技能長在他身上」。

問題因此變成：你要改的是「他每次都表現出來的固定行為」，還是「一份會隨時間變動的資料」？

這裡有個常被忽略的重點：**RAG 的「知識」活在資料庫裡，微調的「知識」活在權重裡。** 資料庫可以改一條、刪一條、立刻生效；權重一旦寫死就難以微調。這正是「固定 vs 會變」這條分界線之所以成立的底層原因。

## 一句話決策框架

**改行為（語氣、格式、固定技能）→ 微調。**
**改知識（會更新的內容）→ RAG。**

> 記住這句靈魂：微調學「固定」的，RAG 供應「會變」的。 如果一個需求兩者都沾，那答案通常是「兩者並用」，而不是二選一。

為什麼界線是「固定 vs 會變」？因為微調是把模式壓進權重，權重一旦固定就不好改——你不可能每逢資料更新就重新訓練一次。而 RAG 每回合都換上下文，資料今天更新、今天就能用。反過來，固定語氣這種東西每次塞進上下文既笨重又不穩定，讓它長進權重反而乾淨。

再補一刀：**這條界線看的是「模式」還是「事實」。** 語氣、格式、流程是有規律的「模式」——適合壓進權重；產品售價、政策條款、人名日期是「事實」——適合放進檢索讓它當下查到。

## 決策表：什麼時候誰贏

| 你的情境 | 較適合 | 為什麼 |
|---|---|---|
| 要模型永遠用特定語氣／格式回覆 | **微調** | 固定行為，塞進權重最穩定 |
| 產品知識每月／每週更新 | **RAG** | 不需動權重，今日更新今日可用 |
| 大量私有、不會變的文件 | **RAG** | 放進檢索比塞進權重便宜可靠 |
| 要教一個「固定技能」的流程 | **微調** | 例：把長文字改寫成固定結構的摘要 |
| 每次輸入都要搭配最新內容 | **RAG** | 上下文天然就是「每回合」的 |
| 兩者都有（語氣＋會變知識） | **並用** | 微調行為，RAG 供知識 |

**RAG 贏**的場合，通常是「知識型」問題：檢索能精確命中、可隨時更新、不用動權重、出錯好修正。**微調贏**的場合，通常是「行為型」問題：語氣、格式、固定風格，這些是「模式」而不是「事實」，用上下文反覆餵既笨又不穩。

## 成本與努力的量級：為什麼「最後才微調」

微調「最後才用」不只是因為效果，更是因為它最重。三種做法從輕到重大概是：

| 做法 | 資料需求 | 更新頻率 | 成本 | 出錯代價 |
|---|---|---|---|---|
| **提示詞** | 無 | 隨時改 | 幾乎為零 | 最低，改一行就修 |
| **RAG** | 需維護索引庫 | 每回合 | 檢索＋向量庫 | 中，換文件即修 |
| **微調** | 高品質示範資料 | 要重訓 | 顯卡訓練 | 最高，動權重、要重驗證 |

看清楚：**越往右越貴、越難改、出錯越痛。** 所以決定順序幾乎總是「先用輕的，輕的撐不住才上重的」。這條「重量」本身就是決策的一部分——需求每季才變一次，微調也許划算；每週都在變，那幾乎肯定是 RAG 的局。

> 另一條務實的線：能用提示詞解決的，別為微調動權重；能用 RAG 解決的，別為微調動權重。 微調該留給「提示詞與上下文都扛不動」的固定模式。

## 常見的誤判

**誤判一：把「該 RAG 的」拿去微調。** 有人希望把整本產品手冊「記進模型」。結果模型把文件背得七零八落，等資料一更新又全錯。手冊是會變的知識 → RAG。

**誤判二：把「該微調的」全推給提示詞。** 一條三十字的固定結尾、一種必須每次複製的措辭，你天天貼在系統提示裡。它能用，但每回合都重來、還容易漏。固定行為 → 微調一次，一勞永逸。

**誤判三：以為微調「取代」RAG。** 兩者幾乎不同層。微調常常是為了讓模型「更擅長把資料用起來」——把一個長文件要塞進上下文前先改寫、再回答。這正是組合拳的開頭。

## 決策流程一圖流

```text
要改變的是「行為」還是「知識」？
│
├─ 行為／語氣／固定技能 ──────────→ 考慮微調
│
├─ 會更新的知識／私有文件 ────────→ 用 RAG（檢索＋上下文）
│
└─ 兩者都有 ─→ 先微調固定行為，再用 RAG 供知識
```

畫成流程就三行。卡住時千萬別停在「二選一」——多半只是你還沒把需求切成「固定的」跟「會變的」兩半。

## 組合拳：先微調行為，再 RAG 供應知識

真正強的系統多半不是二選一，而是分工：

1. **微調**固定那些「每次都要一樣」的部分——語氣、格式、輸出結構。
2. **RAG**負責那些「每次都不一樣」的部分——最新文件、私有知識、正在變的內容。
3. 微調後模型更擅長「讀完檢索到的資料再答」，RAG 更派得上用場。

**兩種典型的組合：**

* **推薦引擎**：微調學「條列式、帶一句理由」的回覆語氣；RAG 塞入「這個使用者最近瀏覽過什麼」。語氣是固定的，資料是活的。
* **內部文件助手**：微調學「先說結論、再附出處」的格式；RAG 從公司的私有知識庫撈最新版文件。兩者各自乾淨。

一個客服模型的例子：你用微調學「先道歉、再用條列點回覆」的語氣；用 RAG 塞入「今天的退貨政策」。各改各的，互不干擾——這才是多數「成功微調」的真實樣貌。

```快速決策偽代碼
# 一行判斷：你要改的是行為還是知識？
if 你要改的是 語氣 / 格式 / 固定技能:
  考慮 微調
if 你要改的是 會更新的知識 / 私有文件:
  用 RAG（檢索 + 塞進上下文）
if 兩者都有:
  先微調固定行為，再用 RAG 供應知識
# 越「重」、越難改、越常變 = 越該往 RAG 靠
```

## 一句話收尾

**微調改的是人（權重），RAG 改的是每一次的午餐（上下文）。** 先想清楚你要動的是哪一層，再決定工具。決定「真的要微調」之後，下一步是學會怎麼便宜地做——那就是 LoRA（`finetune-02-lora`）。

#### Q: 你的產品需要『每次都用固定的商務措辭』，而產品說明書每週更新。最穩妥的做法是？

* 把措辭寫進系統提示詞，說明書也在提示詞裡逐週更新

* 微調學會固定措辭，說明書放進 RAG 由檢索供應

* 全部用微調，把每週更新的說明書也學進權重

* 全部用 RAG，固定措辭也靠每次塞進上下文

> 💡 固定措辭是『行為』→ 微調；頻繁更新的說明書是『知識』→ RAG。組合拳：微調該固定的，RAG 供應會變的。微調學不會常變的知識，RAG 也難以保證每次精準複製固定語氣。
