# 主流向量資料庫比較：從 PostgreSQL 到專用服務

> 📅 2026-08-04 · 工具組
> pgvector、Qdrant、Milvus、Pinecone、Weaviate 各有各的個性。首要決策其實不是「哪家最強」，而是「託管還是自架、融入既有資料庫還是獨立服務」。

---

上一篇講了向量庫「做什麼、何時需要」。現在你真的要選了，打開搜尋一看：pgvector、Qdrant、Milvus、Pinecone、Weaviate、Chroma、FAISS…… 選項多到暈。

好消息是：**在這些工具之間做選擇，跟「哪個模型最強」一樣，不是選「最強」，而是對齊「你在哪裡、要走多遠」。** 這篇把五個主流方案放到同一張桌上，給你一張真實的比較表與一份照做就行的決策指南。

## 先想對邊界條件，再談工具

在比較各家之前，有三個問題會淘汰掉一半選項：

1. **你的資料另外住在哪裡？** 如果你已經在用 Postgres，把向量塞進 pgvector，往往比重架一座獨立的向量服務划算得多。既有基礎設施常是決定性因素。
2. **要自己架，還是要服務幫你扛？** 這決定了你靠的是「運維能力」還是「錢」。
3. **資料量級與查詢模式？** 幾萬顆、單一 filter 就能撐；上百萬顆、要高並發、要混合檢索（`rag-03-hybrid`），才會逼出一座「真正的」向量庫。

把這三題答完，剩下的選擇空間就很窄了。

## 五個選手一覽

| 方案 | 型態 | 一句話定位 | 內嵌還是獨立 |
|---|---|---|---|
| **pgvector** | Postgres 擴充 | 把向量搜尋塞回你已有的資料庫 | 內嵌 |
| **Qdrant** | 獨立服務 | 輕量、專心做向量、API 友善 | 獨立 |
| **Milvus** | 獨立服務 | 為超大規模設計，生態最完整 | 獨立 |
| **Pinecone** | 全託管 | 免運維、呼叫即用 | 獨立（託管） |
| **Weaviate** | 獨立服務 | 內建多模態與 GraphQL，混合搜尋方便 | 獨立 |

Chroma 和 FAISS 也很好用，但性質不同：FAISS 是「函式庫」不是資料庫（不管持久化、過濾、並發），Chroma 更偏「輕量本地方案」。這篇聚焦上面五個真正的「資料庫級」選手。

## pgvector：把一切都留在一處

pgvector 不是一座新的資料庫，而是 **Postgres 的擴充外掛**。資料還是活在原本的表格裡，你只是多了一欄向量：

* **最大的好處是「少一座東西」**：你的文件、metadata、向量、使用者資料全在一個資料庫裡，不需要同步兩套系統。
* 支援 `IVFFlat` 與 `HNSW` 索引，幾十萬顆都穩穩的；百萬級以上才開始吃力。
* 交易（ACID）、備份、權限，全部沿用 Postgres 既有能力——對團隊這是一份免費的信任。

代價是：**它不會為向量拼命**。當你衝到百萬級、要極致延遲時，它不會像專用引擎那麼快。但對「我的資料本來就在 Postgres」的人，它是預設答案。

## Qdrant：輕量而專注

Qdrant 是一套**用 Rust 寫的獨立向量搜尋服務**。它的性格是「專心」：

* 只做向量為主的工作，語意清楚，API 好懂，部署輕。
* 本地端一個 Docker 就能起，也可託管（Qdrant Cloud）。
* 原生支援 payload（metadata）過濾與 payload 索引，搭混合檢索也很順。
* 對中大型專案，它常常是「獨立服務」裡最好上手的起點。

## Milvus：為超大規模而生

Milvus **把向量、metadata、storage 分成不同模組**，天生為「幾億顆向量、分散式部署」設計：

* 功能最完整的生態：分片、複製、容錯、GPU 加速樣樣有。
* 代價是**架構與部署最複雜**——對多數人來說，Milvus 是「真的很大了再來」的選項。
* 維運成本高，不適合拿來當第一個向量庫。

## Pinecone：把運維整個外包

Pinecone 是**全託管（managed）** 的向量服務，你碰不到伺服器：

* 開箱即用，一個 API 就好；縮放、備份、高可用全是它的事。
* 對想「完全不碰運維」、專注在產品的人，這是體驗最好的路線。
* 代價是**錢與耦合**：按用量計費、資料在別人家裡，想要「搬走」就很痛。
* 對原型、對不想僱一整個 infra 團隊的新創，它常常「秒勝」。

## Weaviate：內建多模態與混合

Weaviate 的特色是做「**物件 + 向量」而不只是「向量」**，並把搜尋當一等公民：

* 原生支援**混合搜尋（BM25 + 向量）**與 `rag-03-hybrid` 提到的 reranking，串起來很順。
* 內建多模態（文字、圖片、音訊）模組與 GraphQL API。
* 可自架、也可託管（Weaviate Cloud）。

## MMR 與混合檢索：誰天生就會

`rag-03-hybrid` 會告訴你，檢索不能只有向量一路。這裡直接看各家「天生支援」到什麼程度：

| 方案 | 混合（向量＋BM25） | MMR 多樣性 | 內建重排 |
|---|---|---|---|
| **pgvector** | 要自己串 | 要自己實作 | 無（SQL 層自己兜） |
| **Qdrant** | 原生 Query API | 原生 | 實驗性 |
| **Milvus** | 原生 | 原生 | 原生 Reranker |
| **Pinecone** | 原生 Hybrid Index | 原生 | 第三方搭配 |
| **Weaviate** | 原生 BM25＋向量 | 原生 | 原生 |

**MMR（Maximum Marginal Relevance）** 專門治一個 RAG 常見病：純向量搜尋回傳的 top-k 常常是「同一件事的近義複製品」——比如五段都是講「怎麼退款」，卻沒有「退款期限」那一段。MMR 在「相關」之外再加「多樣性」的加分，讓回傳的段落彼此不重複。

對 RAG 來說，**MMR 是「免費的品質」**：它不要求任何新模型，只是換一種排序方式，卻能讓餵給 LLM 的段落覆蓋更廣。除非你的 query 天生只需要「一段」答案，否則打開它通常穩賺不賠。

## 託管 vs 自架：真正的分岔路口

把上面濃縮成一個最關鍵的二選一：

| 維度 | 自架（pgvector／Qdrant／Milvus） | 託管（Pinecone／雲端版） |
|---|---|---|
| 你需要 | 會顧伺服器、懂部署 | 只想呼叫 API |
| 資料主權 | 完全在自己手裡 | 在供應商機房 |
| 初期成本 | 低（自己機器） | 隨用量浮動 |
| 改動彈性 | 高，可深度調 | 低，受 API 限制 |
| 隱私／合規敏感 | 主場 | 可能要另想辦法 |

敏感資料、需要完全掌控的團隊，幾乎只會走自架；要速度、不要運維的，選託管。**先答這個，再答「哪家」**。

> 一次記住核心：先決定「託管還是自架、塞進既有資料庫還是獨立服務」，然後才是挑牌子。 pgvector 是「資料本就在 Postgres」的預設；Qdrant 是獨立輕量的好起點；Milvus 留給超大規模；Pinecone 給不想碰運維的人。

## 決策指南：照著走一遍

用一張小流程，把你的情境對號入座：

```
① 資料已經住在 Postgres？    是 → pgvector（除非百萬級又極要延遲）
② 真的很大（> 幾億顆）？     是 → Milvus
③ 不想碰任何運維？           是 → Pinecone（或各家的 Cloud 版）
④ 想自架、要輕量獨立服務？   是 → Qdrant（要多模態/混合 → Weaviate）
⑤ 都不到？                   → Chroma / FAISS 就好，別過度工程
```

## 成本怎麼看

「免費」「貴」很容易被誤讀。真正要比的是**總擁用成本**：

* **自架**：機器與電費是死的，查詢再多也不漲——適合量大、可預測的流量。
* **託管**：按 storage 與 query 計費，起步便宜，量一大就浮動——適合前期、波動大的流量。
* **pgvector**：因為共用 Postgres，幾乎是「順便」，最省；但別忘了擴充也是要養的。

給初學者一個務實建議：**先試 Qdrant（自架）或 Pinecone（託管），跑起來、量起來，再想要不要升遷到更「重」的組合。** 別在還沒有一百萬顆向量時，就先背一座 Milvus。

## 下一步

現在你有了工具，接下來是所有工具「合用」的時刻：把嵌入、索引、檢索、生成串成一支端到端的 RAG，還要處理 metadata 過濾與混合檢索——`vectordb-03-with-rag`。

#### Q: 有人說「反正免費」，指的是哪一種選項的真正優勢常被誤讀？

* Pinecone 的按用量計費在量大時反而更划算

* 自架工具的機器成本是固定的，查詢再多也不漲，是「總成本」意義下的省

* pgvector 完全不需要任何資源

* Qdrant 免費但無法用於正式專案

> 💡 自架的機器與電費是固定的，量大不會漲（總擁有成本划算）；託管按用量計費、起步便宜但量大會浮動。『免費/便宜』要放在總成本裡看，別只看單價。
