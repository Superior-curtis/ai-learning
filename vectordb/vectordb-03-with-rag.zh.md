# 與 RAG 搭配：把向量庫變成真正的回答機器

> 📅 2026-08-04 · 使用教學
> 工具都挑好了，現在把嵌入、索引、檢索、生成串成一支端到端管線：喂文件、建索引、檢索、餵 LLM，再用 metadata 過濾與混合檢索取回精準。

---

向量庫挑好了（`vectordb-02-comparison`）。但你真正要的不是「一座資料庫」，而是一個**能回答使用者問題的東西**。這一篇，我們把這塊積木真正嵌進 RAG——從喂進文件開始，到模型吐出一個被正確段落撐住的答案為止。

我會走完一條**完整的端到端管線**，並示範兩件讓它從「能跑」變「能用」的關鍵：metadata 過濾、以及向量＋關鍵字的混合檢索（`rag-03-hybrid` 的落地版）。

## 整套 RAG 的「四拍」

把 `rag-02-chunking` 到 `rag-03-hybrid` 一路走過的零件串成一個循環，其實就四拍：

```
拍① 嵌入 文件 → 切成 chunks → 每段轉向量
拍② 索引  向量 → 放進向量庫，連同 metadata
拍③ 檢索  查詢 → 轉向量 → 過濾 + 混合 → 取回 top-K
拍④ 生成  把「問題 + 取回的段」一起餵給 LLM
```

向量庫佔的是「拍②」和「拍③」。前面 `rag-02-chunking` 決定「能撈到什麼」，這裡決定「撈得快不快、撈得準不準」。一拍一拍走完，缺一不可。

## 一張最精簡的端到端管線

還在為「工具」分心的人，先看這一支最小版本——用 Python 就能跑通全流程（概念範例，實際 API 以你選的函式庫版本為準）：

```概念式：端到端&#x20;RAG（Qdrant&#x20;為例）
# 概念範例，實際 API 以你選的函式庫版本為準
from sentence_transformers import SentenceTransformer
from qdrant_client import QdrantClient
from qdrant_client.models import Distance, VectorParams

embedder = SentenceTransformer("BAAI/bge-small-en-v1.5")
client = QdrantClient(":memory:")                     # 概念用記憶體，正式換大型服務

# 拍① 切塊＋嵌入：假設 docs 是已經切好、帶 metadata 的 chunk
docs = [
  {"text": "退款政策：購買後 30 天內可全額退", "meta": {"dept": "cs", "y": 2026}},
  {"text": "年假規則：每年 10 天，可累積一年",   "meta": {"dept": "hr", "y": 2026}},
]
client.create_collection(
  "handbook",
  vectors_config=VectorParams(size=384, distance=Distance.COSINE),
)

# 拍② 建立索引：向量 ＋ metadata 一起寫進去
for i, d in enumerate(docs):
  vec = embedder.encode(d["text"]).tolist()
  client.upsert(collection_name="handbook", points=[
      {"id": i, "vector": vec, "payload": d["meta"]}
  ])

# 拍③ 檢索：先過濾（只看客服相關），再找最近的
q = "我可以退款嗎"
qvec = embedder.encode(q).tolist()
hits = client.query_points(
  collection_name="handbook",
  query=qvec,
  query_filter={"must": [{"key": "dept", "match": {"value": "cs"}}]},
  limit=2,
).points

# 拍④ 生成：只把「撈回的那幾段」餵給 LLM，不放整庫
context = "
".join(p.payload.get("_text", "") for p in hits)
# 真正上線：把 context + 問題送給模型（此處略）
print(context)
```

注意拍④那段註解：**你只餵「被撈回」的段落給模型，而不是把整個向量庫倒進去。** 這正是 RAG 的精髓——檢索先幫你「剪裁」，生成才不會被塞爆或亂講。

## Metadata 過濾：精準度最便宜的來源

`rag-02-chunking` 要每個 chunk 都帶 metadata。這不是為了好看，而是為了「**先過濾、再算距離**」——這通常是提昇精準度最省力的一步：

```
過濾（便宜，先把範圍縮小）
  └→ 例如 dept = 客服  →  只在客服文件裡找
向量距離（較貴，在縮小的範圍內排序）
  └→ 在客服文件裡，找語意最接近的
```

為什麼它比「多加一個重排器」更划算？因為**過濾是布林、是確定性的**，成本極低、效果極穩；重排是把「語意相近」變成「最對」，貴而且可以之後再上。順序永遠是：**先過濾 → 再混合 → 需要時再重排**。忘掉過濾，你在用一座昂貴的索引去做不該它做的粗活。

> 一次記住核心：過濾比排序便宜又有效——先按 metadata 把範圍縮到該看的，再讓向量在縮小後的範圍裡找最近的。 這是 RAG「能用」與「只是會響」的分水嶺。

## 混合檢索：當向量一個人撐不住

純向量搜尋（`llm-02-embeddings` 的手藝）對「語意相近」很強，但對「精確的字」常漏。真實使用者一天到晚在找「SOP-2024-0715」這種字面上的東西——`rag-03-hybrid` 一整篇都在講這件事的解法。

實作上，向量庫通常支援在**同一次查詢**裡並存向量＋關鍵字：

```
score(chunk) = RRF 合併（向量排名 + BM25 排名）      # `rag-03-hybrid` 的細節
過濾順序：先 metadata 過濾 → 再混合 → 需要時再 rerank
```

對「先撈多一點、再由下一步精篩」的 RAG，混合幾乎總是「至少不輸純向量、在精確字面上明顯贏」。`rag-03-hybrid` 會教你怎麼合併兩種分數、以及何時需要重排。

## 實務上的三個坑

管線能跑之後，真正的翻車通常發生在細節。提早知道這三個坑，可以省掉很多深夜除錯：

* **文件更新了，向量卻沒更新**。改了文件內容，舊 chunk 的向量還躺在索引裡，使用者問到新內容卻找不到。解法：用固定的 `doc_id` 做 upsert（覆寫而非新增），刪除時依 metadata 刪除，別讓幽靈向量默默積灰。
* **top-k 太少或太多**。太少 → 上下文不足、模型只能瞎猜；太多 → 窗口塞爆、token 浪費。從 3–10 開始，之後再依 `rag-03-hybrid` 的重排結果調整，不要一次放 100 段進提示詞。
* **過濾後候選為零**。metadata 條件太嚴（例如某部門根本沒有文件），過濾完一顆向量都不剩，檢索直接空手。上線前先把「過濾空結果」的降級路徑想好——回退到不過濾，總比一片空白好。

## 上線前，照這個順序走一遍

別一上來就追求完美。RAG 是「漸進變好」的，照這個次序逐步加厚：

#### 先跑通最小管線

喂幾份文件、建索引、檢索、餵 LLM，確認「會回答」。這一步只求打通，不求完美。

#### 補上 metadata 與過濾

每個 chunk 帶上 dept、時間、出處，檢索前先過濾。常常這是回收率最高的單一改進。

#### 加上混合檢索

為「精確字碼」這類 query 加上關鍵字訊號，用 `rag-03-hybrid` 的 RRF 合併。

#### 量它，再決定要不要重排

造一個小型評估集跑幾輪，用數字決定是否加 cross-encoder 重排，別憑感覺。

## 走到這裡，下一個變數是「你有沒有在量」

切塊、嵌入、檢索、過濾、混合都就位了——恭喜，你有一座「真的會回答」的系統。但工具箱再齊，仍剩下最後一個變數：**你怎麼知道它變好了？**

改了一版嵌入、調了一次 filter，是變好還是變壞？「感覺變順」不是答案。要把它變成可比較的數字，你需要一套能反覆跑的評估——那是 RAG 系列最後、也最值錢的一塊，回去把 `rag-03-hybrid` 與 `rag-02-chunking` 的收尾重讀一遍，就會發現每一步都在為「可以被量」鋪路。把「量」補上，你的向量庫才真正變成一部回答機器。

#### Q: 為什麼「先 metadata 過濾、再算向量距離」通常是提昇精準度最划算的做法？

* 過濾需要昂貴的模型，但更準

* 過濾是確定性的布林條件，成本低、範圍先縮小，讓向量只在該看的地方排序，比先排序再重排便宜有效

* 過濾可以完全取代向量搜尋

* 過濾只對超大資料庫才有意義

> 💡 過濾是便宜的布林操作，先把範圍縮到該看的（例如只看客服文件），向量距離再在縮小範圍內排序——這比重排那種「把相近變最對」的昂貴手段划算。順序是先過濾、再混合、需要時才重排。
