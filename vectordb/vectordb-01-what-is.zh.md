# 向量資料庫是什麼：何時你才需要一座「語意索引」

> 📅 2026-08-04 · 核心概念
> 嵌入把語意變成座標，但要找「最近的鄰居」，你得先把這幾百萬個座標組織成能快速查詢的結構。這篇講向量庫多做的那件事，以及你什麼時候根本不需要它。

---

上一篇文章 `llm-02-embeddings` 把文字變成了座標：每個 chunk 是一顆向量，語意相近就貼得近。這很棒——但你也許在暗自發愁：「我真的有幾百萬顆向量要放在哪裡？」

答案是：**向量資料庫（Vector Database）**。它不是什麼玄乎的技術，本質上只解決一個問題——**在大量向量裡，快速找出距離最近的 K 個**。這篇我們拆解它「多做的」到底是哪幾件事，更重要的是：**何時你根本不該用一座向量庫**。

## 嵌入只是起點，不是終點

`llm-02-embeddings` 告訴我們：嵌入把「語意相近」變成「空間相近」。這是整個向量世界的哲學前提，我這裡不重講。

但「有向量」跟「能查向量」是兩件事。你手上可能有一萬顆或一百萬顆向量，使用者丟進一句話，你要在**幾十毫秒內**找出跟它最像的那幾顆。光是把這些向量堆在一份記憶體陣列裡，是辦不到這件事的。向量庫存在的全部理由，就是補上「把座標組織成可檢索結構」這一層。

## 相似度搜尋：本質上就是算距離

檢索本身的概念很樸素。`llm-02-embeddings` 提過 **餘弦相似度（cosine similarity）**：把查詢也嵌入成向量，然後跟每一顆已存向量比方向、抓最接近的 K 顆。

```
query ──嵌入──→ [q1, q2, …, q384]
              ↕ 逐顆算餘弦
[v1][v2][v3] … [v1000000]      → 取距離最近的前 K 顆
```

一萬顆，逐顆算一下沒問題；一百萬顆、每一顆 384 維，逐顆掃就是百萬次內積——這正是**慢的來源**。向量庫的核心工作，是想辦法「不用跟每一顆都比」也能找到近鄰。

## 向量庫「多做的」那件事：ANN 索引

向量資料庫與「一份裝向量的列表」之間，差距幾乎全在**索引**。它用的是 **ANN（Approximate Nearest Neighbor，近似最近鄰）**——願意犧牲一點點精確度，換來幾個數量級的速度：

| 索引演算法 | 一句話 | 特性 |
|---|---|---|
| **HNSW** | 分層可導航小世界圖 | 快、準，最常用；佔記憶體較大 |
| **IVF** | 倒排檔案，先分簇再細找 | 省記憶體；要訓練分簇中心 |
| **PQ** | 乘積量化壓縮向量 | 超省記憶體；精度略降 |

「近似」的意思是：它不保證一定回傳「真正的」最鄰近，但實務上通常能找到 95% 以上的正確答案——對 RAG 這種「多撈一點再重排」的場景，這點損失完全不痛。

## 索引之外：向量庫還幫你做三件事

很多人誤會向量庫只是「一個很會搜的陣列」。其實成熟的向量庫還幫你管三件基礎設施的事：

* **動態增刪改**：向量不是一次放進去就永遠不動。文件更新、刪除時，索引要能支援 insert／delete／update，還不會把效能拖垮。
* **Metadata 過濾**：不只是「找最近的」，而是「在『部門＝合規』前提下找最近的」——先過濾再算距離。
* **持久化與並發**：資料要落盤、要能崩潰恢復、要撐住多個使用者同時查。

這三件事，才是「用一個像樣的資料庫」而不是「自己寫個 for 迴圈掃全部」的真正原因。

> 一次記住核心：向量庫做的核心是 ANN 索引——用「近似」換「速度」；而它真正值錢的部分，是圍繞索引的增刪改、metadata 過濾和持久化。 單純「找最近的」你自己寫迴圈就行了。

## 什麼時候你根本不需要向量庫

先潑盆冷水：**不是所有 RAG 都需要向量庫。** 判斷基準是「資料量與更新頻率」：

#### 對照 / Comparison

務實的分界線大概是這樣：

| 情境 | 建議 |
|---|---|
| 幾百日記、幾千個片段，單人用 | 直接載進記憶體逐顆掃，別引入向量庫 |
| 幾萬顆、要過濾、要多人並發查 | 值得上向量庫（Chroma、Qdrant 都行） |
| 上百萬顆、要持續更新 | 非向量庫不可，還得考慮分片 |
| 你的 RAG 只在本地跑、離線 | 輕量方案（Chroma、FAISS）通常就夠，不必上重型服務 |

一個常見的誤區是把「向量庫」想成「一定要的」。對原型、對小型專案，`pandas` 或幾行 FAISS 就夠。**工具是漸進的**：爆了再換，遠比一開始就為它背一座資料庫的運維來得划算。

## 向量庫是「讀重」的：索引建起來很貴

新手最容易忽略的現實是：**建立索引（尤其 HNSW）很花資源**。每插入一批向量都要更新圖結構，成本不像「寫一行資料」那麼便宜。這帶來兩個實務結論：

* **批量匯入**：一次灌一大包，別一千顆一千顆慢慢插——索引重建的開銷是攤平的。
* **錯峰**：大量寫入的高峰期，檢索延遲會稍微變差。把「導入」和「查詢」分開時段，比塞在一起好。

把它想成一本書的目錄：編目錄很費工，但一旦編好，找內容就飛快。**向量庫就是為了「讀快」而生的**——設計系統時，假設你的工作負載是「讀多寫少」，一切就順了。

## 撿幾顆才對：top-k 的直覺

檢索通常不是只看「最接近」的那一顆，而是撿「最近的 K 顆」再交給下一步。K 怎麼定？

* **K 太小（1）**：只要那一顆偏了，答案就全廢，一點容錯都沒有。
* **K 太大（50+）**：把一堆不相關的也塞進提示詞，容易把模型帶偏。
* **常見起點 3–10**：夠容錯、又不會塞爆窗口，之後再配合 `rag-03-hybrid` 的重排調整。

把 K 想成「先撈一小把選項，再讓聰明人去挑」——檢索負責多撈一點，生成負責挑好的。對一個 RAG 系統，K 是少數幾個「改了立刻有感」的旋鈕。

## 向量、函式庫、資料庫：先認清你在哪一層

選型時人常常被「向量資料庫」這個詞統一了，其實它有**三個不同的層級**，適合的情境完全不同：

| 層級 | 例子 | 你會得到 | 少了什麼 |
|---|---|---|---|
| **函式庫** | FAISS、Annoy | 一段算 ANN 的程式碼 | 沒有持久化、過濾、並發；掉電就沒了 |
| **輕量儲存** | Chroma、LanceDB | 會持久化的向量儲存，API 簡單 | 吞吐與彈性有限，適合小專案 |
| **完整資料庫** | Qdrant、Milvus、Pinecone、Weaviate | 索引＋過濾＋並發＋備份一整套 | 多一個要運維的元件 |

很多人「以為自己需要一座資料庫」，其實只需要一個函式庫——用 FAISS 寫個幾行、把向量序列化到磁碟，輕量又好懂。**選錯層級比選錯牌子貴**：為一台腳踏車裝了引擎，運維成本立刻爆表。

## 在 RAG 裡的角色

RAG 的標準管線是「切塊 → 嵌入 → 索引 → 檢索 → 生成」。向量庫坐在「索引 + 檢索」那一格：

```
文件 ──切塊──→ chunks（`rag-02-chunking` 的戰場）
   └─嵌入─→ 向量 ──放進──→ 向量資料庫（建立索引）
                                ↑
query ──嵌入─→ 向量 ──────檢索 top-K────┘
                                ↓
                          query + 這幾段 → LLM 生成
```

關鍵耦合：怎樣的「單位」能被打撈，是 `rag-02-chunking` 切塊決定；向量庫只是負責把切好的東西組織得快。**切得差，向量庫再強也救不回**——它是引擎，不是方向盤。

#### Q: 向量資料庫「最有價值」的貢獻，通常是指哪一件事？

* 把向量存進記憶體排成一列，方便逐顆算餘弦

* 用 ANN 索引做到「近似最近鄰」，用少量精度損失換取大量速度，並附帶增刪改、過濾、持久化

* 讓嵌入模型算得更準

* 自動幫你把文件切成 chunk

> 💡 向量庫的核心是 ANN 索引（近似換速度），但真正值錢的是圍繞它的基礎設施——動態更新、metadata 過濾、持久化與並發。切塊是 `rag-02-chunking` 的事，嵌入是 `llm-02-embeddings` 的事，都不歸向量庫管。
