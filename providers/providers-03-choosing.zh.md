# 供應商選型決策：一套務實的判斷框架

> 📅 2026-08-04 · 核心概念
> 該用一家還是多家？自架還是走 API？把品質、延遲、價格、資料、限流、鎖定六個軸攤開，配一張決策表——選型就不再靠感覺，而是靠優先序。

---

前面幾篇解決了「去哪裡買」（`providers-01-ecosystem`）與「要花多少錢」（`providers-02-pricing`）。現在進入最實際的一問：**我到底該選哪家？該選一家還是好幾家？要不要乾脆自架？**

先潑冷水：這題沒有「唯一正確解」，而且答案會隨你的階段改變。但有**一套可以反覆用的框架**——本質就一句話：**先搞清楚你的優先序，再用六個軸去篩。**

## 六個軸：選型的判斷維度

拿任何供應商，都可以從這六個維度打分。先想清楚你自己的工作負載，再套用：

| 軸 | 你要問的問題 | 關鍵參考 |
|---|---|---|
| **品質（Quality）** | 對『我的任務』夠不夠準？ | 自家任務集，見 `models-06-evaluation` |
| **延遲（Latency）** | 多快吐第一個字？吞吐夠不夠？ | 小模型＋串流通常快 |
| **價格（Price）** | 我的量級下帳單長怎樣？ | 成本算式，見 `providers-02-pricing` |
| **資料處理（Data）** | 資料會去哪？能不能合規？ | 封閉 API 資料經第三方 |
| **限流（Rate limits）** | 每秒/每分鐘上限到哪？ | 各供應商差異很大 |
| **鎖定（Lock-in）** | 換供應商要付出多少重寫成本？ | 統一介面可降低，見 `providers-01-ecosystem` |

六個軸很少全優——**選型的本質就是「用你的優先序做取捨」，而不是「找一個完美供應商」。** 想要延遲最低又最便宜、又絕對合規，那多半不存在；你得決定哪兩個最重要。

## 前兩個軸最容易被誤解：品質與延遲

**品質**：`models-06-evaluation` 講過，「多強」不是一個數字，而是「對誰、對哪類題」。選型時的品質，請一律用你自己的任務集實測——別讓「最新排行榜冠軍」替你決定。跑 15 道你的真實輸入，用你的標準打分，比任何榜單都誠實。

**延遲**：延遲不只是「快不快」，它有三層——**首個 token 時間**（TTFT，感覺多快開始）、**每秒輸出數**（吞吐，多快吐完）、以及**尾部延遲**（最慢的那 5% 有多慢）。對聊天產品，TTFT 決定體感；對批次彙總，吞吐決定成本；對 SLA 敏感的服務，尾部延遲決定你要不要罵人。

## 一套五步的決策流程

把上面的軸，收斂成可以照著走一遍的流程：

#### 先定格優先序

寫下你最在乎的 2–3 個軸（例如「延遲」＋「資料合規」）。這決定了後面篩選的順序。

#### 用自家任務實測品質

拿十幾條你的真實輸入，讓候選各家跑一輪，用你的標準打分——別信排行榜，見 `models-06-evaluation`。

#### 估掉價格與限流

用 `providers-02-pricing` 的成本算式估帳單；查清各家每秒/每分鐘上限夠不夠你的量級。

#### 檢查資料與鎖定

資料能不能進第三方？換供應商的成本高不高？合不合規？不合就一票否決。

#### 決定：一家、多家、還是自架

依結果落到下面的決策表。

## 一家，還是好幾家？

* **一家就夠**：任務單一、範圍穩定。把一條供應商管好最省事，量大還更好談折扣。
* **好幾家**：任務多樣，想要「每種任務都選最合適的模型」；或想要**備援**（一家掛了另一家頂上）；或想用路由把簡單任務丟給便宜模型。代理平台（`providers-01-ecosystem`）讓切換成本變得很低。
* **動態路由（進階）**：用規則或成本自動把請求分流——例如小請求走小模型、難題走旗艦。這已經是「把模型當服務編排」的思路，跟 `agents-01-what-is-agent` 的思考一脈相承。

舉個具體情境：一家新創做客服助手，最常見的 80% 問題用便宜小模型就能答好，剩下 20% 的難題才需要旗艦——那就「多家＋路由」。反之，一家只做「把合約翻成白話文」的單一用途工具，一家旗艦就夠，別自找麻煩。

## 何時該自架（而不是走 API）

要自架，本質上是回到 `models-01-open-vs-closed` 那個分叉：**你得「拿得到權重（開放模型）」＋「願意自己顧部署與維護」**，兩個條件都成立才划算。適合自架的訊號：

* 資料極敏感（醫療、金融、內部機密），**不能出自家伺服器**。
* 量大到「按 token 計費」的帳單，比「機器折舊」還貴。
* 要離線運行、要完全掌控升級時機。

技術地圖回到 `local-ai` 系列：`local-01-ollama` 是入門最友好的起點。

## 給你的決策表

一張把「情境 → 建議」攤開的速查表：

| 你的情境 | 建議 |
|---|---|
| 要最強品質、不想碰運維 | 封閉 API（一家旗艦） |
| 延遲優先、量大又敏感 | 便宜快速模型＋串流，帳單用 `providers-02-pricing` 壓 |
| 資料敏感 / 需完全合規 | 自架開放權重（`models-01-open-vs-closed`） |
| 任務橫跨多種模型最划算 | 代理平台＋多家（`providers-01-ecosystem`） |
| 怕單一依賴 | 一家為主＋一家備援 |
| 剛起步、量還小 | 直接用一家最順手的旗艦 API，先跑再說 |

> 一句話記住選型：「先定優先序，再篩六軸，最後才談『哪個最強』。」 沒有最好，只有「最合你優先序」的組合——而且它會隨你的階段改變，值得每年回顧一次。

## 鎖定（Lock-in）怎麼算成本

鎖定是最容易被低估的軸：你以為「先用了再說」，但**三個月後換供應商，可能等於重寫一半產品**。鎖定的真實成本來自三處：

* **程式介面**：每家 SDK 的呼叫方式略有差異，寫死後就要改。
* **資料與工具**：快取、微調成果、專屬工具（`fine-tuning` 系列談過的 LoRA 等），綁在特定供應商上就帶不走。
* **團隊習慣**：提示詞、評估集、除錯流程，都是遷移成本。

解法不是「永遠不換」，而是**先把介面抽象好**——哪怕只是薄薄一層統一的函式包裝，或乾脆用代理平台（`providers-01-ecosystem`）。把「換」的成本壓低，你才有資格「真的在換」。

## 把選擇當成「會變的」而非「一次定終身」

供應商市場每半年就可能重洗一次：定價會變、模型會換代、開放模型的品質持續逼近封閉旗艦（`models-01-open-vs-closed`）。所以選型不是婚約，是「**每季/每半年重估一次**」的例行公事。只要你把介面抽象得好（或用了代理平台），重估的成本就低——這正是把「鎖定」這個軸壓低的最大槓桿。

## 下一步

選定了供應商，再往底層挖一層，會碰到另一個大問題：**一顆模型「跑一次推理」的成本結構到底長怎樣**——它決定了你該不該在自家土地蓋算力、還是乾脆靠 API。那是 `econ-01-inference-cost` 的主場。把供應商地圖收進口袋，我們往產業的算盤前進。

* 用代理平台轉發到多家封閉供應商
