# Token 計價與比較：看懂帳單的每一塊

> 📅 2026-08-04 · 核心概念
> 模型怎麼收費？看懂輸入 / 輸出 token 兩種價、把一整輪對話的成本攤開，再用快取與批次把帳單壓下來——重點不在『哪個單價便宜』，而在『同樣任務花多少 token』。

---

接上 API 之後的第一個震撼，通常不是「模型強不強」，而是**帳單**。一個不小心，幾千個請求就能讓雲端費用失控，而且常常連「為什麼這麼貴」都講不清楚。這一篇要把「token 到底怎麼算錢」徹底拆開，讓你從「被帳單嚇到」變成「能預測帳單」。

先說結論的骨架：供應商幾乎一律**分開算「輸入」與「輸出」兩種 token**，而你要會的，就是把一整輪對話攤成這兩個數字去算。剩下的都是變數——語言、上下文長度、以及你要不要設法省。

## 兩種價錢：輸入貴、輸出更貴

先記最重要的一張分界。供應商幾乎一律分開計價，而且**輸出通常比輸入貴 2–4 倍**：

| 方向 | 意思 | 相對單價 |
|---|---|---|
| **輸入 token（input）** | 你送出去的提示、上下文 | 較便宜 |
| **輸出 token（output）** | 模型生成的回覆 | 較貴（2–4×） |

為什麼輸出貴？因為**生成**要一步步「抽選下一個 token」（見 `llmcore-01-next-token`），**每抽一個、都要跑一次完整的前向計算**。輸入只需要算一次、就能「孵出」放著等生成；輸出卻是一路上逐 token 生產的。一邊是「算一次就能看」，一邊是「算一遍才吐一個字」，成本自然不同。

## 一次對話的成本怎麼算

還記得 `llmcore-02-tokens` 講過的嗎——**模型計費的單位就是 token**。所以一整輪對話的帳單，就是把它拆成兩條一起算：

```
總成本 =
  輸入 token 數 × 輸入單價
 + 輸出 token 數 × 輸出單價
```

關鍵全在那兩個「token 數」上。重點提醒（`llmcore-02-tokens` 的核心結論之一）：**同一句話，中文的 token 數往往是英文的 2–3 倍**——所以成本也跟著成比例放大。語言、上下文到底塞多大的文件、模型的冗長程度，統統是變數。想省錢，往往先從「少送 token」而非「選便宜的」下手。

## 動手算：一整段對話的帳單

光看公式太抽象，來算一個真實例子。假設你用某個定價的模型（輸入 $3 / 100 萬 token、輸出 $15 / 100 萬 token），算一段「長問答」的花費：

```把一輪對話的成本算給你看
input_price_per_m = 3      # 每 100 萬輸入 token 的美元
output_price_per_m = 15     # 每 100 萬輸出 token 的美元

# 一輪真實的對話：你送一段長提示＋上下文，模型回一段長文
prompt_tokens      = 24_000   # 含長上下文，中文還會拉高
completion_tokens  = 1_600    # 模型生成的回覆

input_cost  = prompt_tokens     / 1_000_000 * input_price_per_m
output_cost = completion_tokens / 1_000_000 * output_price_per_m
turn_cost   = input_cost + output_cost

print(round(turn_cost, 4))   # 約 0.096 美元
```

把這 0.096 美元，乘上「每天幾千次請求」，就是這套應用的每月基線。**先會算，才不會讓它失控。**

## 用 API 自己確認 token 數

不必全部用猜的。每次呼叫的回應都會回傳用量（`providers-01-ecosystem` 提過要記錄），各家 SDK 也常提供計數工具。養成這個習慣：

* 開發時，把 `input_tokens` / `output_tokens` 印出來，看你的提示到底吃掉多少 token。
* 若平台支援，直接調用「純計數」端點，在同一份提示進 API 前先量一次。
* 把這些數字回填到上面的算式，你的成本預估就會從「感覺」變成「帳本」。

## 一張「比價」的正確姿勢：不是比單價

單價最低的模型，不一定最省錢——因為帳單喝的是「token 數」，不是「單價」。用一張示意表看差別（數字只是舉例，非真實報價）：

| 模型 | 每 100 萬輸入 token | 每 100 萬輸出 token | 同一任務實際 token | 估算成本 |
|---|---|---|---|---|
| 便宜小模型 | $0.5 | $2 | 很冗長，還常重試 | 未必低 |
| 旗艦模型 | $3 | $15 | 精簡、一次命中 | 常常更低 |

之所以「貴反而更省」，是因為帳單 = **單價 × token 數**，而 token 數住在「任務」裡，不住在「單價」表上。三個真實的落差：

* **能力更強**：可能一次就答對，弱模型要你重試兩、三次——**重試的 token 往往比貴價還傷**。
* **輸出更精簡**：好的模型廢話少，輸出的 token 少，帳單自然低（尤其輸出比較貴）。
* **上下文打底**：長上下文系統（RAG，見 `rag-01-what-is-rag`）的「輸入 token」才是大頭，多塞一頁資料、每次呼叫就多一份錢。

## 帳單上最容易漏算的陷阱

就算會算公式，還有幾個隱藏項目常被忽略：

* **快取沒命中**：你以為有快取很省，但每次第一筆「快取冷啟動」仍要全價，熱門但隨機變化的提示省不到。
* **工具呼叫 / Agent 循環**：模型回覆裡的工具呼叫也算輸出 token，而 Agent 每轉一輪都在累積輸入——見 `agents-01-what-is-agent`。多輪就是多份錢。
* **多模態**：圖片、音訊的計價往往以「圖片/秒」而非純 token 計，單價可能遠超刷文字的想像（見 `models-03-multimodal`）。
* **時間切換**：部分供應商的快取命中、每日額度生成有「一段時間後過期」的機制，重估期到了就回到全價。

把這四格先填進成本模型，你的預估才會貼近真實帳單。

## 把帳單壓下來：快取與批次

省錢不必靠「選最便宜的」，先把這兩個開關打開，往往立竿見影：

**1. 提示快取（prompt caching）**：把不常變的長上下文（系統提示、長文件、對話歷史）標記為可快取。命中時，那一段輸入 token 的費用會大幅打折（在部分供應商甚至差一個數量級）。對話歷史長、又不太變動的場景，省最多。

**2. 批次（batching）**：有些供應商提供「非即時、但更便宜」的批次端點——傍晚送出、幾小時後拿結果，單價更低。適合離線彙總、夜間排程、大量但不需要即時的生成。

## 一個務實的提醒：先估量級，再談優化

快取與批次很誘人，但別在「量級還沒起來」時就先寫一堆快取邏輯（見 `llmcore-03-context` 對上下文成本的提醒）。務實的順序是：**先用上面的算式估出每月基線 → 若帳單肉眼可見地高，再上快取與批次**。優化是跟著量級走的，不是一開場就做的。

#### Q: 為什麼『輸出 token』通常比『輸入 token』貴？

* 因為輸出比較耗電

* 因為生成是逐 token 逐步抽選，每一步都要跑一次完整前向計算，成本更高

* 因為供應商想多賺你錢，沒有技術原因

* 因為輸出 token 比輸入 token 更長

> 💡 生成不是一次算完，而是像唸詩一樣逐個 token 抽選（見 llmcore-01 的下一個 token 預測），每抽一個都跑完整計算，所以『生產一端』的單價天然更高。
