# 供應商生態總覽：OpenAI、Anthropic、Google…還有更多

> 📅 2026-08-04 · 核心概念
> 想呼叫一個模型 API，這個世界遠不只是 OpenAI。看懂封閉大廠、代理平台與自架三條路線，再弄懂請求、回應、串流與版本那些約定，就掌握了進場地圖。

---

你寫了一支程式，想「呼叫 AI」。腦海浮現的第一個畫面通常是 OpenAI——但真實世界遠比這一間公司寬廣。「供應商」不只是「一家賣模型的廠商」，它是一整塊生態：有封閉大廠、有幫你轉發的代理平台、也有你完全自架的選項。從這裡開始的 `providers-` 系列，要把這整張地圖畫清楚。

先把根基打穩：不管供應商是誰，底層做事的都是同一件事——**預測下一個 token**（`llmcore-01-next-token`）。供應商之間的差別，不在「原理」，而在**你以什麼形式取得這個能力、要花多少錢、資料去向何處、以及誰在管理模型**。這一篇先談「取得的形式」，下一篇談「花多少錢」，第三篇談「怎麼選」。

## 三條路線：先看你在哪條路上

「供應商」可以粗分成三條路線。先定位自己在哪一條，後面才不會迷路：

| 路線 | 代表 | 你控制什麼 | 你被什麼綁住 |
|---|---|---|---|
| **封閉大廠 API** | OpenAI、Anthropic、Google | 幾乎只能「呼叫」 | 按 token 計費、資料經第三方 |
| **代理平台（proxy）** | 各類 Gateway / Router | 選模型、做路由 | 多一層代理、可能多抽一手 |
| **自架 / 開放權重** | Llama、Qwen、Mistral | 權重、部署全部自己來 | 自己顧伺服器與維護 |

這三條線和「開放 vs 封閉模型」完全對得上：那是選擇岔路的**第一個分叉**（`models-01-open-vs-closed`，問「這個模型能不能下載」），這裡的「買 API / 走代理 / 自架」是**第二個分叉**（問「你要用什麼方式把能力接進產品」）。兩者常常重合，但不是同一件事——封閉模型只能走 API，開放權重卻既可以自架、也可以透過某些代理來呼叫。先把這兩張分岔圖疊在腦裡，後面所有決策都有著落。

## 四大主要供應商簡覽

如果想直接「買 API」，通常繞不開這幾位。每個背後的模型家族與性格，詳見 `models-02-families-tour`，這裡只講「呼叫 API」的角度：

| 供應商 | 代表性模型 | 一句話定位 |
|---|---|---|
| **OpenAI** | GPT 系列 | 生態最齊、開箱即用的「預設選項」 |
| **Anthropic** | Claude 系列 | 長文與寫作強、特別重視對齊 |
| **Google** | Gemini 系列 | 多模態天生、與 Google 生態深度綁定 |
| **Mistral** | Mistral / 開放模型 | 歐系起家、小模型效率著稱 |

別把這張表當「排名」——它是「各擅勝場」的地圖。真要比較「誰對你比較強」，用的是 `models-06-evaluation` 那套「自家任務集」的方法，不是看行銷；而「不同模型各自適合什麼」，`models-02-families-tour` 已經帶你逛過一遍。這裡的重點是：**他們都以「API」的形式把能力交到你手上**，而這個形式的長相，出乎意料地一致。

## 呼叫介面長得差不多

好消息是：**這些供應商的 HTTP 介面高度相似。** 每家留給你的都是「一個端點 + 一把 API key」，請求內容幾乎都是「模型名字」加上「一串訊息」，回應則回傳「生成的文字」與「用了多少 token」：

```請求與回應的共通形狀（概念）
# 傳一個「懂 model + messages」的請求過去
model      = "claude-..."
messages   = [ (role=user, content="用一句話解釋 token") ]
max_tokens = 100

# 回應回傳「文字 + 用量」
reply.text          # 生成的文字
reply.input_tokens  # 一次用了幾個輸入 token
reply.output_tokens # 生成了幾個輸出 token
```

各家的欄位名略有出入（例如 OpenAI 回報的是 `prompt_tokens` / `completion_tokens`，Anthropic 回報的是 `input_tokens` / `output_tokens`），但背後是同一個概念——而「token 是什麼、為什麼計費以它為單位」正是 `llmcore-02-tokens` 那篇的核心。概念一致，命名不同，學一次就通用。

### SDK 還是裸 HTTP

各供應商都提供官方 SDK（Python、JS…），也都能用「裸 HTTP」直接打。我的建議很務實：

* **新專案用 SDK**：幫你處理好 key、重試、錯誤型別、串流細節，省一堆踩雷。
* **要深入時再看 HTTP**：多供應商統一介面、低階除錯、代理層轉發時，裸 HTTP 反而清楚。

工具是手段不是目的——SDK 只是把「同一套介面」包裝得更舒服。

### 呼叫前的基本規矩：key 與錯誤處理

任何 API 你都拿到一把 **API key**，就像身分證。幾個務實習慣：

* **key 別寫進前端**：會被抓走盜用。藏在後端 / 環境變數裡。
* **錯誤要處理**：限流時回 429、key 無效回 401、context 太長回 400（上下文上限見 `llmcore-03-context`）。寫好重試與後退，是穩定的基本功。
* **把用量回傳存下來**：每次回應的 token 用量是**你的成本帳本**。記下來，下一篇算帳才不會憑空猜。

## 串流：不必乾等一整份答案

預測下一個 token 是一點一點吐出來的。若等模型「把整段想完」才一次性回傳，用戶要空轉好幾秒，體感很卡。因此主流 API 都支援**串流（streaming）**：邊生成邊回傳，讓你看見字一個一個冒出來：

* **串流**：第一個字立刻出現，體感更快；適合聊天、逐字顯示的介面。
* **非串流**：一次等整份回覆；適合後端彙整、不需要即時給用戶看的場景。

兩者通常只是請求裡多開一個旗標的事，原始程式碼幾乎共用。對「延遲敏感」的產品（`providers-03-choosing` 會談這個軸），串流是預設該開的。

## 「模型的版本」是件事，不是細節

供應商會用**模型名字本身當版本控制**——`claude-3-5`、`gpt-4o`、`gemini-2.0`。這帶出兩個重要習慣：

1. **名字可能對應「會變動的背後實作」**：有些標記（例如帶 `-latest` 或只是慣例）會默默切換它背後真正跑的模型。若你很在意「行為穩定」，就固定用帶**日期戳記**的版本。
2. **升級模型＝改動你的產品**：新版本可能改輸出格式、改行為模式。上線前，先把舊版跑過一遍的「自家任務集」在 `models-06-evaluation` 那套方法下再驗一次。

> 一句話記住版本這件事：「模型名字 === 你的 API 契約。」 名字可能在你以為不變時偷偷變。把版本固定、把驗收測試留著，你才不會被一次「小升級」默默弄壞產品。

## 代理平台：一張卡走天下

介面相似到一定程度，就有人做**代理平台（proxy / gateway）**：用一個統一的介面轉發到多家供應商，讓你用**一把 key、一支程式**就能在各模型之間切換：

* 好處：**可遷移、可對比**——換供應商不需要重寫呼叫程式。
* 代價：多一層網路延遲、可能多一手費用、又多一個第三方要信任。
* 適合：想「兩家都試試」、或想用路由策略（簡單任務丟給便宜模型、難題丟給旗艦）的人。

下面把整個生態畫成一張圖，看「你的程式」能怎麼接：

```text
你的程式
↓ 統一介面（代理平台）
├──→ OpenAI（GPT）
├──→ Anthropic（Claude）
└──→ Google（Gemini）
↓ 或者直接接單一家供應商
單一 API
↓ 或者完全不經過供應商
自架模型（local-ai）
```

## 自架：另一條路

如果你要的是一份「完全控制」——資料不出去、帳單可預期、升級自己定——那 `local-ai` 系列（`local-01-ollama`、`local-02-llamacpp`）和開放權重模型會是你的主場。你不經過任何「供應商的 API」，而是把權重跑在自家機器上。這就是 `models-01-open-vs-closed` 那篇文章的具體落點：買能力有四種位子，選哪個位子，取決於你多在意隱私、成本與控制。

## 接下來該怎麼讀這張地圖

「供應商」不是你要「崇拜」或「效忠」的對象，而是「你手上的工具來源」。讀這張地圖的關鍵動作，是把每一家都當成「可以替換的零件」：介面學一次就通用、版本要固定、key 要藏好、用量要記錄。**把這四件事養成習慣，你在這片生態裡就永遠自由**——換供應商只是換一把 key 的事。

## 下一步

搞清楚「去哪裡買」之後，下一個自然的問題是「**要花多少錢**」——因為 token 計價決定了一整趟生意的成本。看懂帳單要怎麼拆、怎麼用快取與批次壓下來，會是本系列最值回票價的一篇：`providers-02-pricing`。

#### Q: 想在兩家供應商之間『輕鬆切換、做 A/B 測試』，最適合用哪種方式？

* 直接各接一套原始 SDK，寫死兩份程式

* 透過一個統一介面的代理平台，一把 key 切換多家供應商

* 自架開放權重模型

* 把兩家的呼叫程式硬寫得彼此緊密耦合

> 💡 代理平台把『多家供應商』統一成同一個介面，換供應商時不用重寫呼叫程式，正適合比較與遷移。自架則是另一種控制權的位子，跟『想切換』的目的不同。
