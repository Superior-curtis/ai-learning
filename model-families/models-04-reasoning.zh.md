# 推理模型：答案之前的沉思

> 📅 2026-08-04 · 核心概念
> o1/o3、思考模式、努力程度——為什麼有些模型答題前要先『想很久』？它贏在哪、貴在哪，以及你何時根本不需要開啟它。

---

你家那台電腦跑不動的**數學競賽題**，你問普通模型，它可能嘴硬亂答；但如果你問新一代的「推理模型」，它會先沉默一下——那段沉默不是卡住，是它**在自己腦子裡先想了好幾步，才開始講話**。

上一站我們談多模態（`models-03-multimodal`）——模型「看得見」。這篇談它「想得深」：為什麼一大批新模型開始公開炫耀「我會先想一想再回答」，而這個「想」到底值多少錢。

## 一切的起點：還是預測下一個 token

別忘了我們那條唯一的原則（`llmcore-01-next-token`）：模型只會預測下一個 token。推理模型也不例外。所以「推理」到底是什麼？

它的祕密藏在一個巧妙的設計上：**它把「思考過程」也當成要在對話裡輸出的 token。** 普通模型是「問題 → 答案」一氣呵成；推理模型是「問題 → 先輸出一大段內部思考（chain of thought）→ 再輸出最終答案」。

| 步驟 | 普通模型 | 推理模型 |
|---|---|---|
| 收到問題 | 直接開始回答 | 先寫一段內部草稿 |
| 過程 | 一次到底 | 一步步自我推理 |
| 輸出 | 答案（沒有思考痕跡） | 最終答案（思考被藏在幕後） |

這段內部思考又叫**思維鏈（chain of thought）**：把一個難題拆成許多小步，每一步都「說給自己聽」。它是推理模型的引擎，也是最值錢的零件。

## 那段「思考」是怎麼被訓出來的

推理模型那套「先想想再答」不是天生，而是**在訓練階段用對齊技巧（`train-03-rlhf` 那條線）刻意教出來的**：獎勵模型把推理拆成一步步、把自己想錯的路走回來、再給出最終答案。訓練資料裡那些「邊想邊答」的示範，就是它的課本。

所以你可以把「思考」想成：**模型被訓練得願意多花 token，去換正確率。** 它寧可輸出一千個 token 把題目想清楚，也不願五十個 token 草率答錯。**準確率和成本，第一次在模型內部開始互相交易。**

## 為什麼它能在難題上贏

推理模式的威力不是玄學，它有實打實的原因。多步推理任務有一個共同特徵：**錯一步就全錯**。普通模型「一次到底」的答法，等於把賭注全壓在一步上；推理模型則可以走到一半發現「這路不通」，繞回來重想。

| 題型 | 為什麼它強 |
|---|---|
| **數學** | 需要多步演算，每一步都驗證 |
| **程式碼** | 先把問題拆解、再逐一考慮邊界條件 |
| **硬邏輯 / 規律** | 需要遍歷多個假設、排除錯的 |
| **計畫 / 排程** | 需要列舉方案、比較取捨 |

OpenAI 的 o1/o3、以及各家現在提供的「thinking（思考）/ effort（努力程度）」開關，都是在控制「敢想多久」。**開越高，想越久、越準，但也越慢越貴。**

## 代價：不是免費的午餐

推理是要付帳單的。那段「沉默思考」不會免費：

* **更慢**：多寫幾百上千個 token 才作答，延遲暴增。
* **更貴**：那些思考 token 也要計費，成本可能翻好幾倍。
* **更耗電**：對資料中心來說，推理模式是吃電怪獸。

所以「每個請求都開滿推理模式」是極度浪費的做法。你得**判斷這題值不值得它想**。更聰明的方法是分級：簡單題交給便宜快速的普通模型，偵測到難題再升級到推理模式——這正是 `models-01-open-vs-closed` 學到的「按任務選模型」的延伸。

> 記住判斷的一句話：推理模式是給「你真的想不出來、而且答錯有代價」的題目用的。 日常瑣事、簡單查詢、重複任務——開著它，只是白白多花時間與金錢，並不會讓答案變好多少。

## 你何時不需要它

* **日常問答**：早餐吃什麼、這句英文怎麼翻——不值得它想一個月。
* **簡單知識查詢**：模型已經會、或 RAG 就能給答案（見 `llm-03-rag`）。
* **低延遲的產品**：聊天要秒回，誰受得了每次想 30 秒。
* **大批量、重複、無腦**的生成任務：想，是浪費。

原則就一條：**「先想清楚這題簡單還是難；簡單的，別叫推理模型來。」**

一個提示工程視角的類比：**思維鏈（`prompt-03-chain-of-thought`）**本來是我們手動叫普通模型「一步一步想」的技巧；推理模型則是把這件事內建、而且藏在幕後。兩者的界線，比多數人以為的更薄。

## 一次推理過程長什麼樣

拿一道「兩數相乘後再取餘數」的題目，看普通模型與推理模型的差別：

#### 讀題

先確認題目在問什麼，釐清已知與未知。

#### 拆步

把計算拆成：先乘、再取餘，每一步獨立算。

#### 驗算

回頭檢查中間值有沒有算錯、有沒有漏掉條件。

#### 作答

確認無誤後，才把最終答案輸出。

普通模型常常省掉中間兩步——直接跳進作答；推理模型則把這四步都走一遍。**對簡單題，四步是多餘的；對難題，四步是保命符。**

## 在程式上怎麼控制「想多久」

各家 SDK 的參數名不同，但心智模型一致——**用一個參數調思考長度**。偽程式碼長這樣：

```python&#x20;—&#x20;調整推理努力程度
# 偽程式碼：各家的參數名略有不同
# 低 effort：快但粗心；高 effort：慢但細心
reply = client.chat(
model="reasoning-model",
messages=[{"role": "user", "content": "這題怎麼解"}],
reasoning_effort="medium",   # low / medium / high
)
print(reply)
```

實務鐵律：**先從 medium 開始，不夠再加。** 這跟你調溫度（`llmcore-04-sampling`）的心態一樣——預設值通常是最划算的。

## 使用推理模型的三個實務技巧

真要用好它，幾件小事能少踩很多坑：

1. **給它一個「想多久」的目標**：很多模型支援 effort 參數，別一律開最高，中等往往 CP 值最高。
2. **別打斷它**：推理模型中途被打斷，等於逼它交半成品。給它完整的空間想完。
3. **看它想的路徑**：有些模型會公開摘要思考過程。那裡藏著診斷訊號——如果它一直在同一個錯誤假設打轉，問題可能出在題目本身。

## 推理模式反而「扣分」的場景

推理不是只能加分，有些場景它甚至會幫倒忙——「想太多」不等於「想得好」：

| 場景 | 為什麼推理模式反而差 |
|---|---|
| **創意寫作 / 企劃** | 想太多會讓文筆變僵硬，失去靈感與流暢 |
| **開放式議題** | 沒有「標準答案」，想得再深也未必命中 |
| **情緒與語氣拿捏** | 反覆算計往往讓語感變乾 |
| **求快的大型生成** | 成本與延遲雙雙爆炸，品質沒差 |

所以判斷的完整版本是：**推理模式只該用在「有明確對錯、多步、且答錯有代價」的題上。** 偏偏這三類恰恰是工作裡最常被誤用的一片——很多人把創意題也丟進推理模式，結果既慢又僵。

## 把兩者當成「兩個員工」

更健康的比喻是把普通模型與推理模型當成**兩個不同性格的員工**：

* **普通模型**：快手，手腳麻利，日常雜事交給它。
* **推理模型**：慢郎中，深思熟慮，只有重大難題才值得叫醒它。

好的團隊知道什麼時候叫誰。**先過一遍「這題值不值得叫慢郎中」，再決定呼叫誰**——這一小步，能幫你把整張 API 帳單砍掉一大截。這正好呼應 `models-01-open-vs-closed` 與 `models-02-families-tour` 一路強調的：**先想清楚任務，再挑工具。**

* 每個請求都用最高推理模式

* 關掉或設低推理，因為客服多數是日常問答與簡單查詢

* 所有用戶都該等 30 秒的思考
