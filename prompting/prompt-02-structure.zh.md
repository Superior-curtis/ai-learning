# 角色、例子與輸出格式：把結構交給模型

> 📅 2026-08-04 · 使用教學
> 講清楚『要做什麼』只是第一步。要讓模型穩定產出，你得給它三個結構性道具：角色（system role）、幾個好例子（few-shot）、以及明確的輸出格式。

---

`prompt-01-basics` 講的是「把話講清楚」。這一篇要講的是一樣重要的事：**把結構給模型。**

同樣一句「把這段文字改寫得更專業」，你可以只丟一句話讓它自由發揮，也可以告訴它「你是資深編輯、輸出三段、每段最多四行、不要用形容詞」。後者十之八九更接近你要的東西，而且**可以重現**——明天、後天、換一個模型，結果都差不多。

穩定、可重現，這正是工程師愛上提示工程的原因。

## 角色：告訴模型「現在是誰」

「你是一個……」是最常見也最有效的提示開頭。為什麼有用？回到 `llmcore-01-next-token`：模型會從上下文裡推測「接下來最該出現什麼」。你給它一個角色，等於在說「現在的情境是這樣的，請用這個身分的人會用的語言繼續」。

* 「你是資深編輯」→ 語句開始變得嚴謹、愛刪贅字。
* 「你是十年經驗的物理老師」→ 解釋開始注重直覺與類比。
* 「你是 Python 效能工程師」→ 建議開始講 profiling 與複雜度。

角色不是咒語，它只是在幫模型**挑選哪個「語言風格抽屜」**。挑對了，語氣、術語、重視的事就全都對上了。

在 API 層面，角色通常寫在 system 訊息裡；在聊天介面，就是對話開頭那一句「你現在扮演……」。效果一樣。

## Few-shot：用例子示範，比解釋快

有一句老話：**一個好例子，勝過十句描述。**

與其告訴模型「要把語氣調成沉穩而專業」，不如直接給它兩組「輸入 → 輸出」的對照，它自己就能歸納出你要的規律。

```few-shot
把下面這段充滿情緒的話，改寫成冷靜的產品反饋，每條一行。

原文：「這 app 真是爛透了，每次更新都更難用，團隊到底有沒有在聽用戶啊？！」
改寫：「使用者反映近期更新後操作變複雜，建議恢復原本的流程。」

原文：「讚啦，新功能終於來了，等超久，給讚給讚！」
改寫：「使用者對新增的功能表示肯定，並期待後續改進。」

原文：「我快被這個 bug 逼瘋了，重開機一百次了，還是閃退。」
改寫：
```

注意模型是怎麼從例子學到規律的：保留客觀事實、把情緒詞拿掉、語氣中性。你不需要寫「規則十條」，兩三個例子就把規則「示範」出來了。

這就叫 **few-shot prompting**。它特別適合「風格遷移」類任務——翻譯、改寫、摘要、客服口氣。例子越多越接近你想要的，但三到五個通常就夠，太多反而可能讓模型去模仿例子的雜訊。

## 輸出格式：把它變成「可用的」東西

最後一項常常被忽略，但它對「生產力」的影響最大：**明確指定輸出格式。**

* 聊天場景：告訴它「分點列舉、每點一句話」。
* 程式場景：告訴它「只輸出 JSON，不要任何說明文字」。
* 文件場景：告訴它「用 Markdown 標題分三節」。

為什麼這麼有效？因為模型天生「照格式走」的能力很強——它是被海量「填空格式」的文字訓練出來的。你指定格式，它就會把注意力從「該寫什麼」轉移到「怎麼照格式填」，產出直接就能餵給下游工具或腳本。

> 指定輸出格式，是把「聊天玩具」變成「可程式化工具」的關鍵一步。告訴模型『用什麼形狀回傳』，比告訴它『要認真』有用得多。

## 一個 before / after 的小對比

假設你常常要請模型把會議記錄整理成待辦清單。

**Before：**「請幫我把這份會議記錄整理成待辦清單。」

模型會回你一長段、帶點廢話、格式不一的文字。你要手動再清一遍。

**After：**

```structured-prompt
你是專案助理。請把以下會議記錄整理成待辦事項，只輸出 JSON：

[
{ "task": "待辦內容", "owner": "負責人", "due": "截止日" }
]

規則：
1. 每條待辦只列一件事，字數二十字以內。
2. owner 沿用會議記錄中提到的名字，沒提到就填 "未指定"。
3. due 沒提到就填 "未排期"。
4. 只輸出 JSON 陣列，不要任何前言或結語。

會議記錄：
「……小明說下週要完成登入頁的 UI，小華負責後端 API，大數據那塊還沒人認領……」
```

同樣的原始資料，Before 給你一篇要再整理的散文，After 給你一個可以直接餵給 Trello API 的 JSON。差別就在那三樣道具：**角色、例子、格式。**

## 為什麼這樣更「穩」

這三者都在做同一件事：**縮小模型的選擇空間**（呼應 `prompt-01-basics`）。角色縮小「語氣與術語」的選擇，例子縮小「做法與結構」的選擇，格式縮小「長相」的選擇。三層加起來，模型「亂猜」的空間幾乎被關光，所以結果穩定、可重現、好驗證。

這對之後很重要：`prompt-04-robustness` 談的「怎麼讓提示經得起奇怪輸入」，就是建立在「先把它綁得夠緊」之上。

## 當模型不理會格式

偶爾你明確指定了格式，模型還是自己發揮。常見原因有三個：

1. **指令衝突**：系統提示與使用者內容互相打架，模型偏向更晚出現的那個。
2. **格式與內容衝突**：例如「只輸出 JSON」vs「要解釋為什麼」，模型常常選擇「講清楚」。
3. **提示太長**：格式說明埋在五十行裡，模型「看得到」但不「重視」。

解法都指向同一件事：**把格式規則放在最後、寫得最顯眼，並確認沒有互相矛盾的指令。** 這也呼應了 `prompt-04-robustness` 的「綁死長相」。

## 把好提示變成慣例

當你發現某個提示「每次都成功」，別只留在對話裡——把它變成慣例。做法是把成功的那次「角色 + 例子 + 格式」存起來，下次直接複用。

* 寫成一份文件，說明「這是我們客服回覆的固定 prompt」。
* 存進專案設定（例如 `CLAUDE.md`），讓團隊的每次模型呼叫都用同一套結構。
* 版本化：角色、例子、格式每次調整都留下記錄，方便回溯「為什麼以前比較好」。

這一步，是把單次的「成功 prompt」升級成「可重複的資產」。它跟 `train-02-finetuning` 是兩回事——微調是改模型，這裡是用提示把行為固定下來，不需要重新訓練。

| 層級 | 做法 | 成本 |
|---|---|---|
| 個人 | 存在自己的筆記 | 幾乎為零 |
| 專案 | 寫進 `CLAUDE.md` / 設定檔 | 低 |
| 系統 | 版本化、加上驗證與重試 | 中（見 `prompt-04-robustness`） |

## 下一步

你已經會把話講清楚、也會給角色與格式了。接下來是威力最大、也最需要謹慎的一招：**讓模型一步一步推理（chain-of-thought）**——為什麼有效、什麼時候該用、什麼時候反而出錯。見 `prompt-03-chain-of-thought`。

#### Q: Few-shot prompting（給例子）為什麼往往比『用文字描述規則』更有效？

* 例子能讓模型查閱訓練資料裡的原始出處

* 幾個對照例子可以直接示範想要的規律，模型從中歸納風格與結構

* 例子會讓模型更快完成運算

* 模型無法理解抽象的文字描述

> 💡 LLM 從大量文字中學會『接續』，所以對『跟著例子走』特別在行。一組好的輸入輸出對照，等於直接把要的規律示範一遍，比抽象描述更容易被歸納與複製。
