# 量化：用更少的記憶體跑模型

> 📅 2026-08-01 · 深入研究
> 從 FP16 / INT8 / INT4 的位元與範圍講起，拆解量化為什麼可行、GGUF 是什麼，以及品質與大小的實際取捨。

---

一個 70B 的模型，光是權重就要占多少記憶體？如果每個權重用 16 位元存，答案是 70 × 10⁹ × 2 bytes ≈ 140 GB——超過大多數消費級硬體。這篇文章拆解「量化（Quantization）」：它如何用更少的位元存模型、為什麼幾乎不會崩壞，以及你該怎麼選。

## 先搞懂那些數字

模型權重是浮點數，不同精度代表不同的位元數與數值範圍：

| 型態 | 位元數 | 能表示的範圍（約略） | 常見用途 |
|------|--------|----------------------|----------|
| FP32 | 32 | 巨大，~1e-38 到 ~3e38 | 訓練累積、數值基準 |
| FP16 | 16 | 窄，~1e-4 到 ~6e4 | 加速推理與訓練的主流 |
| BF16 | 16 | 範圍同 FP32，精度較低 | 訓練穩定的主流 |
| INT8 | 8 | -128 到 127（整數） | 推理量化，幾乎無損 |
| INT4 | 4 | -8 到 7（整數） | 極度壓縮，稍有損失 |

關鍵直覺：**浮點數把位元「浪費」在可以很小、也可以很大的指數上；整數把整個範圍都拿來表示「刻度」**。量化做的事，就是把每個浮點權重「壓」到一個整數刻度，再用一小組參數（scale 和 zero-point）把它還原成接近原值。

### 記憶體怎麼算

模型的記憶體需求主要是權重，公式非常簡單：

```
記憶體（bytes）= 參數量 × bytes_per_param
```

以常見的 7B 模型為例：

| 精度 | bytes/參數 | 7B 權重佔用 | 相對 FP16 |
|------|-----------|------------|-----------|
| FP16 / BF16 | 2 | ~14 GB | 1×（基準） |
| INT8 | 1 | ~7 GB | 0.5× |
| INT4 | 0.5 | ~3.5 GB | 0.25× |

再加上 KV cache 和啟動值（activations），實際需求量會更高，但權重永遠是最大宗。這就是為什麼「把 7B 模型從 FP16 降到 INT4」可以把一張 8GB 顯示卡的界線，變成可以順跑的體驗。

## 為什麼量化可行

聽起來像是「把精度丟掉」，但實務上運作良好，有三個原因：

1. **權重有冗餘**。神經網路有大量參數，彼此互相補償；把每個權重從 16 位元降到 8 位元，平均而言對輸出的影響很小。模型像一個團隊，一兩個人記錯數字，整體結果仍大致正確。
2. **模型對雜訊本來就夠穩健**。訓練過程本身就有大量雜訊（隨機批次、學習率），神經網路天生能容忍小誤差。
3. **逐層縮放（per-channel scaling）**。不同通道的權重範圍差異很大，量化時給每個通道各自的 scale，誤差就能大幅降低。

### 品質怎麼被衡量

量化的損失通常用困惑度（perplexity）或下游任務分數來測。對 7B–8B 等級的模型，INT8 幾乎無感，INT4 通常也還能接受；但**越小、越舊的模型，對量化越敏感**，損失可能明顯。

## 量化技術的家族

* **訓練後量化（PTQ）**：模型訓練完後再轉，最常見。像 `bitsandbytes` 的 `load_in_4bit`，一行就完成。
* **量化感知訓練（QAT）**：把量化誤差納入訓練過程，品質更好，但要重訓，成本高。
* **GGUF 的 k-quant**：這是 llama.cpp 生態的量化格式（Q4_K_M、Q5_K_S、Q8_0 等）。`_K` 代表「用更精細的方式對重要張量分組量化」——K-quant 是近年把 INT4 品質拉起來的關鍵。

```python
# bitsandbytes 範例：載入時直接轉成 4-bit
from transformers import AutoModelForCausalLM, BitsAndBytesConfig

config = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4")
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Llama-3.1-8B",
    quantization_config=config,
)
```

## GGUF 與 llama.cpp

在本地跑量化模型，最常見的組合是 **GGUF 檔案格式 + llama.cpp**。GGUF 是把模型權重、tokenizer 和量化參數打包成單一檔案的格式，特別適合 CPU 推理，也支援 GPU 分層卸載。

用 Ollama 一行就跑起來：

```bash
ollama run llama3.1:8b-instruct-q4_K_M
```

用 llama.cpp 手動執行：

```bash
# 先下載 Q4_K_M 的 GGUF 檔（例如從 Hugging Face）
llama-cli -m models/llama-3.1-8b-instruct.Q4_K_M.gguf \
  -p "Explain quantization in three sentences." -n 256
```

檔名裡的 `Q4_K_M` 是品質代碼：`4` 是位元數、`K` 是 k-quant 演算法、`M` 是混合策略（關鍵層用多一點位元）。

## 實際取捨：品質 vs 大小

沒有免費的午餐，但這道菜幾乎免費。以 Llama 3.1 8B 的常見選項為例：

| 量化 | 權重大小 | 品質 | 適合場景 |
|------|----------|------|----------|
| Q8_0（INT8） | ~8.5 GB | 接近原始 | 記憶體夠用、追求品質 |
| Q5_K_M | ~5.5 GB | 很好 | 一般本機使用的好平衡 |
| Q4_K_M | ~4.9 GB | 好 | 記憶體有限的最佳預設 |
| Q3_K_M | ~4 GB | 可接受 | 最後手段，大模型迫不得已 |
| Q2_K | ~3.1 GB | 明顯下降 | 幾乎不建議 |

選型時的決策樹：

* **記憶體吃得下 FP16/INT8？** 用最高的，別多想。
* **記憶體只能吃 INT4？** 優先選 k-quant 的 `Q4_K_M`，而不是舊式 `q4_0`。
* **模型越大，量化越「划算」**。70B 的 Q4 只損失一點點品質，卻省下 100+ GB——大模型對量化更耐受。
* **注意 kv cache**。上下文越長，KV cache 越大；長上下文時要算進去，別只看權重。

## 總結

| 概念 | 一句話 |
|------|--------|
| 精度 | FP32 / FP16 / BF16 / INT8 / INT4，位元數與範圍不同 |
| 記憶體 | 參數量 × bytes_per_param；7B 從 FP16 的 ~14GB 可降到 INT4 的 ~3.5GB |
| 為什麼可行 | 權重冗餘 + 模型對雜訊穩健 + 逐層縮放 |
| GGUF / llama.cpp | 打包量化模型的檔案格式與推理引擎，本機推理的主流 |
| 取捨 | 位元越低越小越快，但品質略降；大模型對量化更耐受 |

量化讓我們能把「只在雲端跑得動」的模型，塞進筆電和手機。理解位元、記憶體公式和 k-quant 的命名，你就掌握了選擇的關鍵：**在品質與大小之間，找到你的平衡點。**
