# 混合檢索與重排：向量不是唯一的排序標準

> 📅 2026-08-04 · 深入研究
> 向量搜尋對「語意相近」很強，對「一模一樣的詞」反而常漏掉。關鍵字 + 向量混合、再交給 cross-encoder 重排，是目前最可靠的檢索配方。

---

上一篇文章我們把文件切好、嵌入、存進向量索引。結果你發現一個詭異的現象：問「退款政策」它找得很好，但使用者打了一串**精確的代碼**——「SOP-2024-0715」——向量搜尋卻把完全不相干的「2024 年會議記錄」撈了回來。

這不是 bug。這是向量搜尋的天性：它比的是**語意**，不是**字面**。而真實世界裡，使用者常常就是在找「那個字面上的東西」。這篇講怎麼用**混合檢索（hybrid retrieval）**補上這個盲點，再用**重排（reranking）**讓排序更貼近真正的需求。

## 向量搜尋的盲點：精確比對

嵌入把「語意相近」變成「空間相近」，這招對近義詞、換句話說很強。但代價是：

* **精確識別字元碼**（產品型號、合約編號、人員工號）容易被稀釋成「泛指」。
* **專有名詞、縮寫**（如「CI/CD」「LLM」）在向量空間裡常被當成一般詞。
* **冷門卻精確的句子**，與其語意近的候選不多時，相關分數都不高。

`llm-02-embeddings` 說嵌入是「把語意放進座標空間」——而座標空間沒有「一模一樣」的概念。關鍵字檢索正好相反，它對字面異常敏銳。

## BM25：關鍵字檢索的現代版

傳統的關鍵字檢索（關鍵字掃描整份文件）太笨，現代標竿是 **BM25**：

* 對每個查詢詞，看它在候選文件中出現的**頻率**；
* 並用「這個詞在**多少份**文件出現」當懲罰——「的」「the」這種到處都是的詞沒價值，稀有的詞才有區分力。

```
query: "SOP-2024-0715"
BM25 計分 → 出現這個字串的那個 chunk 分數最高
向量計分 → 語意接近但字面不同的一大票 chunk 分數差不多
```

BM25 不「理解」語意，但它是**精確比對**的王者。把兩者結合，正是「理解」與「查得到」的合體。

## 混合：兩種訊號一起算

混合檢索的直覺很簡單：**兩邊都搜，再把結果合併**。問題在「怎麼合併」——向量分數和 BM25 分數是完全不同的尺度，不能直接相加。

最常用的解法是 **RRF（Reciprocal Rank Fusion）**：不看分數，只看**排名**。每個候選在各個榜單上的名次越好，加權越高：

```
score(doc) = Σ 1 / (k + rank_of_doc_in_list_i)      # k ≈ 60 是常見設定
```

排名為 1 的候選貢獻最大，之後急速衰減。RRF 的好處是**不需要調權重、不怕尺度不一致**，把「這個東西在向量榜排第 2、在關鍵字榜排第 5」化成一個可比的數。

用數字看更清楚。假設向量榜與 BM25 榜各有 4 個候選，k = 60：

| 候選 | 向量排名 | BM25 排名 | RRF 分數（≈） |
|---|---|---|---|
| chunk A | 1 | 3 | 1/61 + 1/63 ≈ 0.0324 |
| chunk B | 2 | 5 | 1/62 + 1/65 ≈ 0.0315 |
| chunk C | 10 | 1 | 1/70 + 1/61 ≈ 0.0307 |
| chunk D | 5 | 4 | 1/65 + 1/64 ≈ 0.0310 |

chunk A 兩邊都排前面，穩穩第一；chunk B 在向量榜排第 2 所以緊咬；chunk C 雖然 BM25 第一，但向量榜掉到 10，總分反而被 B、D 壓過。這正是混合想要的：**兩邊都好，勝過一邊極好另一邊漏**。

### 另一條路：加權得分合併

RRF 是「排名派」；還有一派是「得分派」——把兩邊分數各自正規化到同一尺度（例如各自縮放到 0–1），再乘上加權係數相加：

```
combined = α × vector_score + (1 − α) × bm25_score      # α ∈ [0, 1]
```

得分派的優點是**能調 α**：如果你的資料多是精確代碼，就把權重重壓向 BM25；多是長篇散文，就壓向向量。代價是**多一個要調的超參數**，而且正規化方式一變，結果就漂。對多數人，RRF 的「零參數」通常是更穩的起點——先跑起來，真的需要再換得分派去精調。

## 為什麼混合勝過純向量

| 情境 | 純向量 | 混合（向量 + BM25） |
|---|---|---|
| 換句話說、同義句 | 強 | 強 |
| 精確代碼、型號、編號 | 常漏 | 一次命中 |
| 縮寫、專有名詞 | 會被稀釋 | 字面兜底 |
| 冷門但精確的長句 | 分數平庸 | 有機會上榜 |
| 拼寫略有出入 | 仍可語意命中 | BM25 幫不上，靠向量 |

大方向不變：**混合至少不輸純向量，而在「精確比對」這類向量最弱的場景，它明顯贏。** 代價只是多跑一次關鍵字檢索——以現代檢索器的速度，幾乎可以忽略。

> 一次記住核心：向量是「理解」，關鍵字是「查得到」，RAG 兩個都要。 混合檢索（向量 + BM25）先把候選拉回一個較大的池子，這一步寧可多撈，交給下一步去精篩。

## 重排：讓排序變「聰明」

混合檢索解決了「**找得到**」，但排序仍粗糙——向量分數和 BM25 分數各自有偏見。接下來交給**重排器（reranker）**，通常是 **cross-encoder**：

* 早期的雙塔嵌入（bi-encoder）把問題和文件**分開**各自編碼，快但沒讓兩者「互相看」。
* Cross-encoder 把「問題 + 每個候選」**拼在一起**送入模型，讓模型真正「讀一遍這段跟問題搭不搭」，慢但準。

實務上是**兩段式**：

```
第一段（快）：向量 + BM25 混合，撈回 top 50~100
第二段（準）：cross-encoder 逐個打分，重排成 top 5~10
```

這正是 `llm-03-rag` 提過的「調低 K、加 reranker」的落地做法。第一段要寬（別漏），第二段要準（留好的），兩段分工，速度和品質兼得。

```text
問題 ──→ 向量檢索（top 50）──┐
│                          ├─→ 合併（RRF）→ top 50~100
└──→ BM25 檢索（top 50）──┘            │
↓
cross-encoder 重排 → top 5~10
│
↓
問題 + 這幾段 → LLM 生成
```

## 實務上的坑

幾個混合檢索常見的失誤，提早知道能省很多事：

* **只調一方**：把 K 調小、或只加關鍵字不加向量，都會回頭失去另一種訊號的覆蓋。兩邊的 K 都要夠大，重排才選得出好料。
* **忘了 metadata 過濾**：混合檢索是「更會撈」，但精準度仍然靠過濾。先過濾、再混合、再重排，三件事是順序不是選項。
* **重排器的取捨**：cross-encoder 比雙塔慢，所以一定要排在「候選已縮小」之後。候選池太大，重排反而成為瓶頸。

## 何時可以省掉重排

重排很有效，但它不是義務。要不要加，取決於「第一段檢索已經夠不夠用」：

| 情境 | 需要重排嗎 | 理由 |
|---|---|---|
| 資料量小、query 種類單一 | 常可省 | 向量 + BM25 第一段已很乾淨 |
| top-k 拉回來的雜訊很多 | 需要 | 多一次精篩能洗掉噪音 |
| 精準度要求很高、錯了會出人命 | 需要 | 這是把「相近」變成「最對」的最佳工具 |
| 延遲預算極緊 | 要取捨 | cross-encoder 是整段管線最慢的一環 |

判斷依據不該是「有沒有」，而是「**第一段撈上來的 top-k，廢物佔多少**」。廢物多，就值得用 `rag-04-evaluating` 證實重排的有效性；幾乎不超過容錯度，就別為它付出延遲。

## 接下來

到這裡，檢索端已經從「撈得回」進化成「撈得回 + 排得好」。但你怎麼知道它真的變好了？「感覺變順了」不是證據——你要的是把檢索和生成**分開量**，並且有一套可以反覆跑的測試集。這正是整個系列最實用的一篇：`rag-04-evaluating`。

#### Q: 混合檢索為什麼比純向量搜尋更穩健？

* 因為混合會把候選池縮得更小，重排更快

* 因為向量負責語意、BM25 負責精確字面比對，兩者互補，尤其在代碼編號等場景一次命中

* 因為 BM25 能完全取代向量搜尋

* 因為混合之後就不需要 metadata 過濾了

> 💡 純向量強於語意但弱於精確比對；BM25 正好相反。混合把兩種訊號都納入（通常用 RRF 合併），在純向量最弱的「精確代碼」場景明顯補強。
