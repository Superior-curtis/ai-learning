# 切塊與索引：把文件拆成能撿的單位

> 📅 2026-08-04 · 使用教學
> RAG 撿的是「chunk」，不是整份文件。切多大多小、要不要重疊、怎麼保留標題與 metadata，決定了檢索找不找得到那個關鍵答案。

---

RAG 的第一步是切塊（chunking）——把一份文件拆成一個一個可以「被撿起來」的小單位。這是最不起眼、卻最決定成敗的階段：**檢索只能撿你切出來的 chunk**。沒切好的話，後面所有階段（重排、評估）都是在幫你補救一個可以在一開始就避免的問題。

這篇給你不踩坑的切塊心法、切完怎麼嵌入建立索引、以及為什麼「只存向量」是新手最容易漏掉的事。

## 為什麼一定要切塊

你不能把「整份 200 頁的手冊」當成一個單位拿去檢索，原因有二：

1. **語意會被稀釋**。一部手冊的主題太多，把它壓成一顆向量，等於把「甜點食譜」和「退款政策」混在同一座標裡，搜哪個都不精準。
2. **檢索顆粒太大**。即使它被搜中了，你也得把整本 200 頁塞進提示詞——窗口一下就爆，`llm-03-rag` 說的「只餵需要的」瞬間破功。

所以要把文件切成「**一個 chunk 剛好承載一個可回答的單元**」——通常是一個能自我獨立的主題或答案。

```
整份手冊 ──切──→ [chunk① 離職流程][chunk② 年假規則][chunk③ 薪資結構]
                    ↑ 檢索撿的是這些小單位，不是整本
```

> 一次記住核心：chunk 是檢索的最小單位，你撿不到你沒切出來的答案。 如果某個答案橫跨兩個 chunk 中間，除非有重疊，否則檢索很可能兩個都撿不到。

## chunk 大小：Tradeoff

切多大沒有唯一正解，但方向很清楚——太大太小都有代價：

| 大小 | 優點 | 代價 |
|---|---|---|
| **過小**（小於 100 tokens） | 精準、噪音少 | 上下文太少，語意不完整，容易缺上下文 |
| **適中**（300–800） | 平衡精準與完整 | 需要實測微調 |
| **過大**（>1500） | 上下文完整 | 語意被稀釋；夾帶不相關內容；塞爆窗口 |

好的切入點是 300–800 tokens（約 1–3 段），然後**用實際查詢去測**，別猜。判斷基準是「夠不夠讓模型獨立答對一個問題」——漏了答案就是太小，塞了一堆無關就是太大。

## Overlap：別把答案切在邊界上

切塊最怕的意外是：關鍵句子剛好被一刀切成兩段，前半在 chunk A、後半在 chunk B。檢索時哪個都「相關但答不出來」。

解法是讓相鄰 chunk **重疊（overlap）**一小段，常見 10–20%：

```
chunk① [….…A 段落….…| 重疊開頭]
chunk②          [重疊尾巴| B 段落….…]
        ↑ 剛好被切到邊界的句子，兩邊都保留完整
```

重疊不是越多越好——太多等於重複儲存、浪費 token。10–20% 通常足以讓「切在邊界上的答案」在兩側都完整出現。

## 按結構切，別只按字數

純粹「每 N 個字一刀」最省事，也最容易切出半句話。更好的做法是**沿著文件的自然結構切**：先按標題 → 章節 → 段落，再在必要時細分。

關鍵是**保留結構資訊**。兩個技巧特別實用：

* **帶標題**：把章節標題加到 chunk 內容裡，→ 檢索能靠標題判斷主題。
* **Contextual chunk**：嵌入時把「這 chunk 屬於哪一章、前文講了什麼」一起拼進去，檢索品質常明顯提升，`llm-03-rag` 提過這個手法。

## 依內容類型選策略

不是所有文件都用同一套切法。不同內容有各自「天然的最小單位」：

| 內容 | 適合的切法 | 原因 |
|---|---|---|
| 連續散文（文章、手冊章節） | 300–800 tokens，按段落與標題 | 一個段落往往就是一個可回答單元 |
| 程式碼 | 按函式／類別／單元切，保留縮排 | 半個函式沒有意義，檢索單位是「一段可執行邏輯」 |
| 表格 | 一列或一小塊表格為一單位，連同表頭 | 表頭是那一列語意的「錨」，別弄丟 |
| 帶頁碼的 PDF | 先依版面抽出文字，再依頁／節切 | 版面切碎文字，直接切會得到割裂的半句 |

判斷標準始終一樣：**切成「這個 chunk 能不能獨立回答一個問題」。** 對程式碼是「能不能獨立理解這段邏輯」，對表格是「這個欄位連同它的含義」。

## 口訣：先放大，再用真實查詢校準

切塊沒有公式，但有個可以照做的次序：

```
① 先按文件結構切（標題→章節→段）
② 若有 chunk 仍太大，再在段落內部依語意細分
③ 加上 overlap 10–20%，避免答案卡在邊界
④ 用「最難的 10 個真實查詢」驗收：每個都能被某個 chunk 完整承接嗎？
```

第四步特別值錢。抓幾題使用者「最容易問卻最難答」的，逐一確認「這個答案完整落在哪個 chunk」。只要有一題「答案被切碎了」，就是該回頭調切法的訊號——而這個判斷，最後還是要用 `rag-04-evaluating` 的數字來定案。

## 嵌入 + 向量索引

切好的 chunk，下一步就是「讓它變得可以被語意檢索」——這正是 `llm-02-embeddings` 講的嵌入：

* 每個 chunk 用嵌入模型轉成一個向量。
* 所有向量一起存進**向量索引**（FAISS、Chroma、Qdrant、pgvector 等）。
* 查詢時，問題也轉成向量，在索引裡找「最近的 K 個」（常見 top-k = 3–10）。

嵌入細節不重複講，這裡只留一句提醒：**切塊大小必須跟嵌入模型的最佳長度匹配**——多數嵌入模型對「很長的一段話」分數會退化，這是支持「切小一點」的另一個理由。向量庫怎麼選、什麼時候才需要，見 `vectordb-01-what-is`。

## 別只存向量：Metadata

新手最常犯的錯：把向量寫進資料庫就收工，只留了 embedding 和原文。這會讓你**搜得回內容，卻過濾不了、也說不清來源**。

每個 chunk 應該跟著一串 metadata，至少要有：

| Metadata | 用處 |
|---|---|
| `doc_id` | 這個 chunk 屬於哪份文件 |
| `source` / `url` | 可以拿來當引用出處 |
| `heading` / `page` | 章節或頁碼，方便定位與過濾 |
| `updated_at` | 資料新鮮度判斷 |
| `tags` / `department` | 業務層的過濾條件 |

Retrieval 前先按 metadata 過濾（「只看 2026 年的」、「只看合規部門」），能大幅減少雜訊、提升精準度——**過濾比排序更便宜、更有效**。

```概念式：切塊&#x20;+&#x20;存向量&#x20;+&#x20;存&#x20;metadata
# 概念範例，實際 API 以你選的函式庫版本為準
from sentence_transformers import SentenceTransformer
import chromadb

embedder = SentenceTransformer("BAAI/bge-small-en-v1.5")
client = chromadb.PersistentClient(path="./chroma")
collection = client.get_or_create_collection("handbook")

def chunk_with_overlap(text, size=400, overlap=80):
  chunks, start = [], 0
  while start < len(text):
      chunks.append(text[start : start + size])
      start += size - overlap          # 重疊 20%
  return chunks

doc = load_manual()                      # 你的文件
for i, chunk in enumerate(chunk_with_overlap(doc)):
  vec = embedder.encode([chunk]).tolist()
  collection.add(
      ids=[f"doc1:{i}"],
      embeddings=vec,
      documents=[chunk],
      # 只存向量會後悔 → 一定要帶 metadata
      metadatas=[{"doc_id": "doc1", "section": f"page-{i}", "updated": "2026-08-01"}],
  )
```

## 切塊的品質，最後還是要秤

切塊沒有「一眼看出對錯」的檢查表，真正的裁判是檢索結果——而檢索結果要有**數據**才算數（Recall、精準度）。沒有測量，你只是在「猜」哪個大小比較好。等到我們講 `rag-04-evaluating`，你就能把「切得好不好」變成一個可以量、可以比較的數字。

下一篇，我們讓檢索從「單靠向量」升級成「混合」——解決向量搜尋最想不通的一個盲點：`rag-03-hybrid`。

#### Q: 為什麼說「你撿不到你沒切出來的答案」？

* 因為檢索只能在已建立的 chunk 中找，若答案被切在兩塊之間且無重疊，兩塊都「相關但答不出來」

* 因為嵌入模型會把沒切到的部分自動補齊

* 因為向量索引可以找出文件中被省略的文字

* 因為模型會靠自己的記憶補上缺失的 chunk

> 💡 檢索的最小單位是 chunk。若答案橫跨兩塊中間又沒有重疊，兩塊都只有一半答案，檢索往往都撿不到能獨立答對的那塊。
