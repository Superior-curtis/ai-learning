# 評估 RAG 系統：把「感覺還行」變成數字

> 📅 2026-08-04 · 深入研究
> RAG 有兩個獨立要量的事：檢索撈得準不準、生成有沒有忠於來源。不量檢索，改了不知道變好變壞；不量忠實度，幻覺會藏在流暢裡。

---

走到這裡，你的 RAG 已經能跑：切塊、嵌入、混合檢索、重排、生成，一條龍。然後有人問：「**效果好嗎？**」你只能回答「呃，感覺還行」。

「感覺還行」不是一種度量，它也不會告訴你**下一步該改什麼**。RAG 系統最貴的不是運算，是「改了一版，卻不知道變好還是變壞」。這篇教你怎麼把「感覺」換成「數字」——而且拆成兩個獨立、必須分開量的事。

## 兩個問題，要分開量

RAG 的回答品質，是**兩段失誤疊加**的結果。你不把它們拆開，就會永遠不知道錯在哪一段：

```
檢索段：資料庫裡明明有答案 → 有沒有撈回來？   ← 檢索品質
生成段：撈回來的段落 → 模型有沒有忠實引用？  ← 生成品質
```

檢索再準，模型不肯照著講，答案也是編的；模型再忠實，檢索撈錯段落，答案一樣錯。**所以要兩套指標。**

## 檢索品質：Recall 與 Precision

衡量檢索最常用的兩個數字，沿用資訊檢索的經典：

| 指標 | 問的是 | 簡單算法 |
|---|---|---|
| **Recall（召回）** | 該撈到的，撈到了幾成 | 命中的相關 chunk ÷ 總共該有的相關 chunk |
| **Precision（精準）** | 撈上來的，有幾成是真的相關 | 命中的相關 chunk ÷ 撈上來的全部 chunk |

用 `rag-02-chunking` 的話說：Recall 低 = **答案沒被切出來、或沒被檢索命中**（chunking／檢索的鍋）；Precision 低 = **撈回一堆雜訊**（過濾、重排、K 值的鍋）。看哪個指標掉，就能定位到哪個階段。

## 生成品質：Faithfulness

檢索對了，接著量「**模型有沒有忠於來源**」。這個概念叫 **faithfulness（忠實度）**：

* **高忠實**：模型回答裡的每個斷言，都能在檢索回的段落裡找到支撐。
* **低忠實**：模型寫得通順，但摻了它自己的「記憶」——這就是 `llmcore-05-hallucination` 的場景，只是來源變成了「自以為懂」。

務實的量法：對每個回答，請人（或一個評分模型）把回答拆成一句句斷言，逐句檢查「這句有沒有被上下文支撐」。算出「有支撐的比例」就是忠實度分數。

> 一次記住核心：檢索用 Recall / Precision 量「找得到」，生成用 faithfulness 量「不亂講」。 兩者是乘法不是加法——任何一段為零，整體就是零。先修低的那段，比平均用力有效。

```概念式：算一份評估集的&#x20;Recall&#x20;與&#x20;faithfulness
# 概念範例，實際 API 以你選的函式庫版本為準

# 題目只有 5 題時，一張表就夠：
evals = [
  {"qid": 1, "relevant": ["c3", "c4"], "retrieved": ["c3"],        "claims_grounded": 2, "claims_total": 2},
  {"qid": 2, "relevant": ["c7"],        "retrieved": ["c2", "c7"],  "claims_grounded": 1, "claims_total": 3},
  {"qid": 3, "relevant": ["c1"],        "retrieved": [],            "claims_grounded": 0, "claims_total": 0},
  {"qid": 4, "relevant": ["c5"],        "retrieved": ["c5", "c9"],  "claims_grounded": 2, "claims_total": 2},
  {"qid": 5, "relevant": ["c8"],        "retrieved": ["c3"],        "claims_grounded": 1, "claims_total": 1},
]

def recall(e):   return len(set(e["relevant"]) & set(e["retrieved"])) / len(e["relevant"])
def precision(e):return len(set(e["relevant"]) & set(e["retrieved"])) / max(1, len(e["retrieved"]))

print("avg recall   =", sum(recall(e)   for e in evals) / len(evals))
print("avg precision=", sum(precision(e) for e in evals) / len(evals))
print("faithfulness =", sum(e["claims_grounded"] for e in evals) / max(1, sum(e["claims_total"] for e in evals)))
```

這三行輸出就是你的 RAG「儀表板」。題目少沒關係，數字會告訴你「瓶頸在檢索還是在生成」——Recall 低是撈不到，faithfulness 低是亂講。

## 建立一套小型評估集

你不需要一開始就做一千題。先建一套**小而穩定**的集子，能反覆跑就夠了。原則是用 `Steps` 分四步：

#### 收集真實問題

從使用者紀錄撈 30–50 題最常問的。沒有紀錄就找業務單位「假裝當使用者」寫。真實分布遠勝你憑空想的問題。

#### 標注 ground truth 段落

對每題，人工指出「正確答案在文件哪一段」。這份標注是 Recall 的分母——沒有它，Recall 無從算起。

#### 寫下「理想答案」

不用逐字，給一段「完整答案該覆蓋的要點」即可。它是 faithfulness 與回答品質的基準。

#### 固定住，反覆跑

把這套集子存成測試，每次改 chunking／檢索／提示詞都跑一遍，記錄分數。從這裡開始做改良決策。

只有 30–50 題看似很少，但「少而穩、能重跑」遠勝「多而亂、跑一次就忘」。評估集的價值在**可重現**，不在數量。

## 離線 vs 線上：評估也要分兩種

上面這套是「**離線評估**」——在部署前，對固定集子量分數，幫你做決策。生產上還需要「**線上監控**」，看實際使用時的品質有沒有漂移：

| 維度 | 離線評估 | 線上監控 |
|---|---|---|
| 時機 | 改版前後 | 上線後持續 |
| 資料 | 固定測試集 | 真實使用者流量 |
| 量什麼 | Recall / Precision / faithfulness | 失敗率、退回率、滿意度代理指標 |
| 目的 | 「這版可以上嗎」 | 「上線後有沒有變糟」 |

實務建議：**先有離線集子，再談線上監控。** 沒有離線集子，線上監控收集到的失敗也無法定位「是哪一段改了造成的」。資料庫、查詢分布都會變——定期（每季）重抽一份新測試集，別讓數字停留在半年前。

## 常見失敗模式

一旦開始量，你會反覆撞見幾種典型失敗。先認得它們，除錯快得多：

| 症狀 | 根因 | 修法 |
|---|---|---|
| 檢索 Recall 低，答案在庫裡卻撈不到 | 答案被切在 chunk 邊界、或語意偏冷門 | 加 overlap、按結構切、contextual chunk |
| 撈回一堆不相關（Precision 低） | 過濾不足、K 太大、沒有重排 | metadata 過濾、調 K、加 reranker（見 `rag-03-hybrid`） |
| 撈到的 chunk 相關但不含答案 | 撈到「鄰居」而非「正主」 | 檢查 chunk 邊界、提高 recall、確認答案切得出來 |
| 檢索對、生成卻編造 | 提示詞沒強制引用、或模型自恃懂 | 「只依據上下文」+ 允許說不知道、降低語氣溫度 |
| 一直錯同類題目 | 資料本身缺一段、或某個來源過時 | 回頭修資料，不是修模型 |

值得注意最後一列：**RAG 錯得很「誠實」——錯在哪，往往就是哪個環節的責任。** 檢索型錯誤和生成型錯誤，修法完全不同，所以第一件事永遠是先定位。

## 把「改進」變成閉環

有了這套數字，RAG 改良就從「靈感驅動」變成「實驗驅動」：

```
改動（chunking / 檢索 / 提示詞）→ 重跑評估集 → 看 Recall、Precision、faithfulness
         ↑                                        ↓
         └────────── 保留變好的，回滾變差的 ──────────┘
```

每次只改一件事，用同一套集子比較，你就擁有了對 RAG 系統的「儀表板」。這在生產環境裡重要到可以獨立成一篇——也是 `finetune-01-finetune-vs-rag` 討論「該微調還是該修 RAG」時，唯一的客觀依據：數字告訴你瓶頸在哪，再決定錢往哪花。

#### Q: RAG 的檢索 Recall 一直偏低，但 faithfulness 很好。最可能的問題出在哪？

* 模型不肯照上下文回答，需要換提示詞

* 答案在資料裡但沒被撈回來——通常是 chunking 或檢索端問題，例如答案被切在邊界、或語意偏冷門

* 重排器把正確的 chunk 排到後面去了

* 不需要修，Recall 低不影響使用

> 💡 Recall 量的是「該撈到的有沒有撈到」，faithfulness 量的是「撈到的有沒有忠實引用」。Recall 低而 faithfulness 高，代表檢索端把對的段落漏掉了，跟生成端無關。
