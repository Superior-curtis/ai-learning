# 為什麼要 RAG：別讓模型靠記憶瞎掰

> 📅 2026-08-04 · 核心概念
> 模型的知識是凍結的、窗口是有限的、它還會自信地編造。RAG 把「搬相關資料進提示詞」這件事系統化，是讓模型拿你的資料說真話的第一步。

---

你有沒有問過一個明顯「它應該知道」的問題，結果它給了一個完美、流暢、卻完全錯誤的答案？比如你公司的離職流程，或是上週剛改的定價。模型不是在騙你——它只是被逼著「憑記憶作答」，而它的記憶早已凍結、且有限。

這篇文章回答為什麼要 RAG。如果 `llm-03-rag` 教的是「管線長什麼樣」，這篇講的是「為什麼非得這樣」。一切問題，都可以從模型最基本的三個限制推出來。

## 三個限制，一個解法

模型不是萬能的百科。它的「世界觀」建立在三個大腿上，而每一條都撐不起「用我的資料回答」這個需求：

| 限制 | 意思是 | 對應的坑 |
|---|---|---|
| **知識凍結** | 訓練一結束就再也不更新 | 不知道訓練後的新聞，沒看過你的私有文件 |
| **窗口有限** | 一次只能看固定數量的 token | 貼不進整份文件，對話久了前面的被擠掉 |
| **自信編造** | 沒有「我不知道」的機制 | 不知道時傾向掰出聽起來合理的內容 |

前兩個來自「模型是無狀態的」這個事實，第三個是它「預測下一個詞」本性的副產品。三條加在一起，註定了「讓模型直接回答你家公司的問題」注定翻車——除非我們插手輸入。

## RAG 到底在解決什麼

RAG（Retrieval-Augmented Generation，檢索增強生成）把上面三個問題，用同一個動作一起解決：**在模型開口前，先從外部資料庫把相關內容「撿」回來，塞進提示詞，讓模型照著參考資料回答。**

```text
問題 ──→ ① 檢索：從你的資料庫找相關段落
│
↓
② 增強：問題 + 相關段落 拼進提示詞
│
↓
③ 生成：模型依據參考資料回答
（每一步都沒改模型本身，只改「它這次看到了什麼」）
```

* 它**繞過**知識凍結：你的資料庫隨時可以更新，不用重新訓練。
* 它**繞過**窗口限制：不貼整本書，只貼相關的幾段（這正是 `llmcore-03-context` 提的「只餵需要的」）。
* 它**壓低**幻覺：模型手上有證據可循，還能說「這裡沒有，我不知道」（對比 `llmcore-05-hallucination` 的成因）。

一句話：RAG 不是給模型「裝記憶」，而是**每次需要時，把對的舊內容搬回窗口**。

> 一次記住核心：RAG 不修改模型，只修改輸入。 它不改變模型學到的能力，而是改變模型「這次回答時手上有什麼」。這是它跟微調最本質的差別，也決定了兩者怎麼分工。

## 把心智模型掛回「預測下一個詞」

這套設計不是繞口令，它完全從 `llmcore-01` 的核心把戲推出來：**模型只會做一件事——看眼前這一段文字，預測下一個最合理的詞。**

由此得到兩條鐵律：

* **模型是「沒有參考資料的普通話連連看玩家」。** 你餵它什麼，它就基於什麼接下去講。沒餵相關資料，它只能憑訓練時留下的「印象」接，而那個印象是凍結的。
* **要讓它答你的資料，就得把資料放進它的「視線」裡。** 視線 = 上下文窗口（`llmcore-03-context`）。RAG 的全部工作，就是「在它開口前，把相關資料搬進視線」。

一旦你用這個角度想，RAG 就不再是某種特效，而是**對「無狀態文字預測器」的正確使用方式**：你控制它看什麼，它負責把話接完。

## 增強：怎樣才算真的「讓它照著講」

光把段落塞進去還不夠——模型很可能「看了但不聽」，繼續用自己記憶回答。所以「增強」這一步，除了拼湊上下文，還要**用提示詞把它的行為鎖住**：

```概念式：把「照上下文答」寫進提示詞
# 概念範例，實際 API 以你選的函式庫版本為準
system = (
  "You are a helpful assistant grounded in the context below. "
  "Answer ONLY from the context. "
  "If the context cannot answer the question, say you do not know. "
  "For every claim, cite which document supports it.\
\
"
  "### CONTEXT ###\
" + "\
\
".join(f"[doc {i}] {c.text}" for i, c in enumerate(top_k))
)

final = system + "\
\
### QUESTION ###\
" + query
answer = call_llm(final)
```

三個能寫進提示詞的要點，等於把 `rag-04-evaluating` 的「忠實度」提前變成設計原則：

* **「只依據上下文」**：給模型明確的命令，別讓它自恃懂。
* **允許說不知道**：讓「資料裡沒有」成為合法答案，幻覺的最大來源就被堵住。
* **要求標註引用**：逼模型指出「這句是哪份文件撐的」，也讓使用者能查證。

## 為什麼說「增強」而不是「搜尋」

「檢索」聽起來像 Google，但 RAG 不只幫你找到……它還幫你**用**。真正的價值在最後一段：檢索回來的段落，不是丟給人看，而是丟給**生成模型**，讓模型把多段證據組織成一段人話，而且能指出是哪份文件支撐哪個斷言。

搜尋滿足的是「我要那筆資料」；RAG 滿足的是「我要一個**基於資料**的答案」。兩者目標不同，評量方式也不同——這點留到 `rag-04-evaluating` 細講。

## RAG vs 微調：為什麼先選 RAG

「要不要讓模型懂我家公司」通常有兩條路。RAG 改**輸入**，微調改**模型本身**。除非你的目標是「學一種固定技能／風格」，否則九成先從 RAG 開始：

| 維度 | RAG（改輸入） | 微調（改權重） |
|---|---|---|
| 改的是 | 每次的回答素材 | 模型的能力本體 |
| 資料更新 | 改資料庫即時生效 | 要重新訓練 |
| 成本 | 每次多讀幾段 token | 一次訓練，貴且慢 |
| 可解釋 | 能引用來源段落 | 知識埋在權重裡，無法指出處 |
| 適合 | 大量、會變動的事實資料 | 固定行為、語氣、格式 |

兩條路不是互斥——很多生產系統是「RAG 負責答事實，微調負責對齊語氣」。但當你不確定該先做哪個，先把 RAG 做對，通常錢花得更少、成效更可控。完整決策我們在 `finetune-01-finetune-vs-rag` 深入比較。

## 什麼時候 RAG 不夠

也該知道 RAG 的邊界，避免把它當銀彈：

* **需要跨多份文件推理**：一次檢索給的上下文常不夠，需要多輪檢索或結合工具呼叫。
* **需要真正即時的最新資料**：RAG 只能檢索「你索引過」的內容，實時資料要靠 API 呼叫。
* **需要模型本身的推理能力**：RAG 給資料，推理仍是模型的活；`models-04-reasoning` 那類模型另有用武之地。

## 把故事走一遍

把概念串成一個具體場景，RAG 就很好懂了。假設你公司有一本員工手冊，使用者問：「我離職前要把公司筆電寄回去嗎？」

**沒有 RAG**：模型沒看過這本手冊，它會從「印象」裡湊一段「一般來說離職流程是……」——聽起來合理，但不是你們公司的答案。

**有 RAG**：

1. 問題先向量化，在索引裡撈出「離職」相關的幾個 chunk。
2. 提示詞裡塞進這些段落，並註明「只依據以下內容回答」。
3. 模型讀到手冊原文「離職時請將公司資產（含筆電）於最後工作日後三天內歸還」，據此回答，還能指出「出處：員工手冊第 7 節」。

同一個模型、同一套權重，有 RAG 就是「有憑有據」，沒有就是「憑印象瞎猜」。差別全在輸入那一刻。

## 接下來

RAG 的四段管線（檢索 → 增強 → 生成）裡，最容易決定成敗、也最常被忽略的是最前面那段：**怎麼把文件切成一段段可以檢索的 chunk**。切得好，後面評估、重排都省力；切得差，模型再強也救不回。

下一篇，我們把整份文件「拆成能撿的單位」——`rag-02-chunking`。

#### Q: 「RAG 不改模型，只改輸入」這句話，最準確的意思是？

* RAG 會把新知識訓練進模型權重

* RAG 讓模型每次都先載入相關的外部段落再回答，模型本身的參數不變

* RAG 只是把搜尋結果顯示給使用者，不進提示詞

* RAG 需要重新微調模型才能生效

> 💡 RAG 在生成前把相關資料搬進提示詞（修改輸入），模型權重完全沒變。這是它跟微調最本質的差別，也說明為什麼資料更新可以即時生效。
