# MCP 是什麼：AI 世界的 USB-C

> 📅 2026-08-04 · 核心概念
> 每次接新 AI 工具都要寫專屬整合，MCP 就是為了解決這件事而生的開放標準。拆解它解決的問題，以及 Host、Client、Server 三個角色怎麼分工。

---

你桌上有五台裝置，每一台都要用不同的充電線：A 用圓頭、B 用方頭、C 要帶轉接器、D 乾脆只有無線充電。你每換一台裝置，就要多帶一條線——這就是今天「接 AI 工具」的真實感覺。

過去幾年，每個 AI 工具都像一台「只能用自己專屬線材」的裝置。想讓聊天機器人查資料庫，你要寫一套「查資料庫的整合」；想讓它讀檔案，再寫一套「讀檔案的整合」；想讓它訂機票，又一套。每個服務都有自己的呼叫方式、參數格式、錯誤處理。開發者大量的時間不是花在「讓模型變聰明」，而是花在「把工具接上去」。

`agents-03-mcp` 已經帶你看過 MCP 在整個 Agent 生態系裡的輪廓。這一篇是 mcp 系列的起點，任務更簡單：**把「MCP 到底解決了什麼」講清楚**。不吹不黑，老實說。

## 問題：每個工具都要重新接線

先精確定義問題。假設你是一位 Agent 開發者。模型本身已經會「預測下一個詞」——這是 `llmcore-01` 反覆強調的基礎——但要讓它真正「做事」，你得給它工具。而每個工具背後都連著一個真實系統：資料庫、檔案系統、Slack、GitHub。

問題就出在這裡，而且是一層層疊上去的：

* **每個服務都是獨一無二的。** Slack 的 API 和 GitHub 的 API 長得完全不一樣；呼叫方式、回傳格式、認證流程都是各家自訂。
* **整合是一份持續的功。** 別人改版 API，你的整合就跟著壞；你追著修，對方又改。
* **Agent 框架各說各話。** 同一個工具，A 框架有一套接法，B 框架又有一套，C 框架再一套。

於是「接一個新工具」變成一件成本高、又常常重做一遍的事。更糟的是，這些努力幾乎無法累積：今天為「接 Slack」寫的整合程式，明天換一個框架就作廢，得從頭再來。

一句話總結這個痛點：**連接的工具越多，重複的功夫越多，累積的資產越少。**

## 解法：把「接線」變成標準

MCP（Model Context Protocol，模型上下文協定）要解決的就是這件事：**把「Agent 如何連到工具」標準化。**

請注意它「不是」什麼——它不是一個服務，不是一個框架，甚至不是一套綁定的 SDK。它是一份「大家同意的規則」，定義了：

* 工具長什麼樣（名稱、描述、參數格式）
* 用戶端和伺服器怎麼握手、怎麼對話
* 呼叫結果怎麼回傳、錯誤怎麼表示

MCP 最常用的比喻就是 USB。USB 出現之前，鍵盤、滑鼠、印表機各有各的插頭，互不相通；USB 出現之後，一條線走天下。MCP 想做的是同一件事——只是這次要接的不是周邊設備，而是「AI 能用的工具」。

> USB 標準化的不是「每個設備內部怎麼運作」，而是「每個設備怎麼被連接」。MCP 標準化的不是「每個工具內部怎麼實作」，而是「每個工具怎麼被 Agent 呼叫」。這是理解 MCP 最重要的一句話。

把「以前 vs 現在」攤開看，對比會很清楚：

| 過去：每個工具一套接法 | 現在：一個標準，處處相容 |
|---|---|
| 每個 API 都要寫專屬整合 | Server 寫一次，任何 Client 都能連 |
| 參數格式各家不同 | 一律「名稱 + 描述 + JSON Schema」 |
| 換框架就要重寫 | 標準與框架無關，只談規則 |
| 整合無法累積 | 寫好的 Server 可以互相共用 |

## 三個角色：Host、Client、Server

MCP 的架構只有三個角色，先記住他們的分工：

* **Host（主機）**：你正在用的應用程式——比如 Claude Code、Claude 桌面版、或你自己寫的 Agent 程式。它負責跟使用者互動，也是整個對話的「主持人」。模型、上下文、決策迴圈都住在這裡。
* **Client（用戶端）**：Host 內部的「接線生」。每個 Client 對應一個 Server，負責用標準格式跟那個 Server 對話，把 Server 的能力翻譯回 Host。
* **Server（伺服器）**：把某個能力包成標準介面的人。比如「天氣伺服器」把天氣 API 包起來，「檔案伺服器」把檔案系統包起來。它是離 Host 最遠的那一層。

一次記住這個關係：**一個 Host 可以養多個 Client，一個 Client 連一個 Server，一個 Server 提供一批工具。** 你想讓 Agent 同時會查資料庫、會看 Git 歷史、會發 Slack 訊息？那就各接一個 Server，讓它們並排站好。

## 一次請求的旅程

把上面的角色套進實際運作，一次工具呼叫大概長這樣：

#### Host 探問

Host 想知道「這個 Server 有哪些工具可用」。

#### Client 代跑

Client 用標準格式向 Server 發送 tools/list。

#### Server 交名冊

Server 回一份標準的工具清單——名稱、描述、參數 Schema。

#### 模型挑工具

模型讀完清單，判斷這個請求該用哪個工具，發出 tools/call。

#### Server 幹活

Server 執行真正的動作——真的去查資料庫、真的去發訊息。

#### 結果回流

結果以標準格式回到模型上下文，模型繼續預測下一個詞，把結果組織成回答。

第 3 步之後是最關鍵的轉折：**模型拿到的是標準化的工具描述，根本不需要知道 Slack 或 GitHub 的 API 長什麼樣。** 你只需要把 Server 包好，剩下的交給標準去接。

## 用天氣當例子走一遍

抽象落不了地，就換一個具體案例：你想讓 Agent 會查天氣。

1. **Server**：你（或社群）寫一顆「天氣伺服器」，把天氣 API 包成一個標準工具 `get_weather`，用 JSON Schema 宣告「傳城市名，回溫度與天氣狀況」。
2. **Client**：在你的 Agent 程式裡放一個 Client，用 stdio 或 HTTP 連上這顆 Server。
3. **Host**：你對 Agent 說「台北明天會下雨嗎」。Host 裡的模型看到 `get_weather` 的描述，判斷該用它，自動帶上 `city: 台北` 呼叫。
4. **結果**：Server 去天氣 API 查詢，把結果以標準格式回傳；模型把數字組織成一句人話回答你。

從頭到尾，你沒有寫一行天氣 API 的整合程式碼——連接是標準的，查詢是 Server 做的。這就是 MCP 想帶給每個工具的效果。

## 誤解與澄清

MCP 走紅的同時，誤解也跟著長出來。挑三個最常見的：

* **誤解一：MCP 是一個具體產品。** 它不是。它是協定、是一份規則。你不用任何官方 SDK，照著規格自己實作一個 Server 也完全合法。
* **誤解二：用了 MCP 就不用寫程式。** 恰恰相反——工具背後的邏輯還是要你寫，MCP 省的是「連接」的功，不是「實作」的功。
* **誤解三：MCP 只適合大公司。** 剛好相反，它是開源標準，個人開發者甚至業餘玩家都能參與——`mcp-03-build-your-own` 會證明這件事。

## 誰在推 MCP

MCP 由 Anthropic 於 2024 年底開源，但它的關鍵字是「開放」：規格公開、SDK 開源，任何公司、任何框架都能實作。

* **Agent 應用**：Claude 系列產品原生支援，愈來愈多 Agent 框架把 MCP 當成接工具的預設介面。
* **社群伺服器**：資料庫、GitHub、Slack、瀏覽器……社群寫好的 MCP Server 快速累積，裝一顆就能用。
* **整個開發社群**：標準之所以成立，不是因為「一家大廠在推」，而是因為大家都接得上。這是 MCP 與「私有 SDK」本質上的不同。

## 不誇大的老實話

MCP 這幾年被講得很熱，但值得先把話說清楚：

* **它不是唯一標準。** 還有別的協定在競爭；MCP 只是目前被最多人接受的其中一個。「USB-C」這個比喻講的是標準化的威力，不是說它已經一統天下。
* **它不保證安全。** 把工具開放給模型，等於把「能動系統的手」交出去。工具是新的攻擊面，這在 `security-07-agent-security` 會詳細展開。
* **它不讓工具變神奇。** Server 還是要有人寫、有人維護。MCP 省的是「接線」的功，不是「蓋系統」的功。

但方向是對的：當「接線」變成標準，每一份寫好的整合都不再是一次性的資產，而是可以在任何支援 MCP 的 Agent 裡重複使用的公共基礎建設。這是整個生態系能持續累積的關鍵。

## 快速 FAQ

#### MCP 一定要用 Anthropic 的產品嗎？

不用。MCP 是開放協定，任何支援它的 Host 都能用；Anthropic 只是發起者之一。

#### 一個 Host 最多能接幾個 Server？

沒有硬性上限。實務上取決於記憶體、工具清單長度，以及模型一次能不能接住那麼多選擇。

#### MCP 的 Server 只能由 Agent 呼叫嗎？

主要是。但因為介面是標準的，人也能直接跟 Server 對話，例如除錯時手動發一組 JSON-RPC 訊息。

## 記住一句話

MCP 解決的不是「模型不夠聰明」，而是「工具接不上」。把工具接入變成標準之後，每一份整合都從「做一次」變成「累積一次」。下次聽到有人說「MCP 就是 Agent 世界的 USB-C」，你知道他真正想講的是：**標準化連接，讓整合可以共用、可以累積。**

#### Q: MCP 標準化的是哪一件事？

* 標準化每個 AI 工具的內部實作方式

* 標準化 Agent 如何連接並呼叫工具

* 標準化模型如何預測下一個詞

* 標準化所有工具的資料儲存格式

> 💡 MCP 管的不是工具內部怎麼運作，而是連接介面：工具怎麼被描述、怎麼被呼叫、結果怎麼回傳。它像 USB，統一的是插頭規格，不是設備本身。
