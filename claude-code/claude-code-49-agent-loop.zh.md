# 一次任務的生命週期：Claude Code 代理迴圈逐步拆解

> 📅 2026-07-28 · 核心機制
> 用互動式步驟導覽，把 Claude Code 執行一次任務的完整迴圈拆給你看：從輸入到輸出，每一步內部到底發生什麼。

---

Claude Code 之所以能「自動做事」，不是因為模型有多神奇，而是因為它把一次任務拆成一條可以重複的迴圈：**決策 → 執行 → 觀察 → 再決策**。這篇文章用互動式導覽，把這條迴圈一步步拆開。

> 建議搭配 模擬器頁面 一起看——那裡的每一步都能點出真正的 prompt 與 payload。

## 迴圈的五個階段

#### 接收輸入

你打出一段話，Claude Code 收到一個 user message。這可能是「幫我修個 bug」，也可能是一大段需求。

#### 組裝上下文

它把 Git 狀態、CLAUDE.md、系統提示詞、歷史對話全部收集起來，組成一個完整的 context window。

#### 呼叫模型

把組裝好的上下文送給模型。模型吐出兩種東西之一：純文字回應，或一個「我想用某個工具」的請求（tool\_use）。

#### 執行工具

如果是 tool\_use，就真的去執行——讀檔、跑測試、搜尋。工具的回傳結果（tool\_result）再送回上下文。

#### 迴圈到完成

回到「呼叫模型」這一步，重複直到任務完成或到達上限。最後把結果組裝成給你的文字回應。

## 關鍵：工具是「行動」的開關

模型的強項是「理解」與「規劃」，但真正動手的是工具。這就是為什麼 Claude Code 的架構裡，工具系統佔了很大比重。

> 記住這個心智模型： 模型負責「想」，工具負責「做」。每一次 tool\_use 都是一次「我想做這件事」的請求，Claude Code 負責執行並把結果送回。

## 一個實際的迴圈示範

下面是一個簡化的終端示範，模擬 Claude Code 執行一次「跑測試並修復失敗」的任務：

```text
$ claude "跑測試，修掉失敗的那個"
✦ 我來先看看測試狀態。

$ Bash: npm test
FAIL  checkout.test.js
✗ should calculate total correctly

$ Read: src/checkout.ts
…已讀取 42 行
→ 發現 tax 計算順序錯誤

$ Edit: src/checkout.ts
已套用修改（1 行）

$ Bash: npm test
PASS  checkout.test.js
✓ 所有測試通過
```

注意到中間那兩步了嗎？**Read → Edit → 再跑測試**，這就是迴圈的威力：每一步的結果都變成下一步的輸入，直到達成目標。

## 上下文壓縮：迴圈為什麼不會爆

你可能會問：迴圈跑很多圈，上下文不會爆掉嗎？答案是：會。所以 Claude Code 有**分級壓縮**機制，超過視窗大小時依重要性壓縮歷史。

#### 壓縮的原則

「最重要的保留，其次摘要，最不重要的丟棄」。對話核心與當前任務最相關，通常保留；較舊的附屬內容會被摘要或捨棄。

#### 使用者能做什麼

你可以手動 /compact 壓縮對話，或 /clear 完全重來。對長任務來說，偶爾手動壓縮能讓模型專注在真正重要的上下文上。

## 設計上的取捨：為什麼不是「一次算完」

你可能想：為什麼要迴圈？直接一次把任務算完不是更快嗎？

#### 對照 / Comparison

```text
單次呼叫
一次丟「幫我修測試」
→ 模型直接給出
　完整的修改結果
優點：快
缺點：看不到中間狀態
　無法邊做邊驗證
```

```text
代理迴圈
多次迭代
→ 讀檔 → 修改 → 跑測試
→ 根據結果再調整
優點：每一步都驗證
　能處理不確定性
缺點：較慢
　消耗更多 token
```

代理迴圈用「多一點延遲」換「每一次行動都被驗證」。對真實的程式碼任務，這幾乎總是更值得。

## 檢查你的理解

#### Q: tool\_use 訊息代表什麼？

* 模型已經完成了任務，等待使用者確認

* 模型表達「我想執行某個工具」，由 Claude Code 去跑

* 工具執行失敗的錯誤訊息

* 工具正在背景偷偷運行

> 💡 tool\_use 是模型發出的「行動請求」，不是結果。真正的執行發生在下一步：Claude Code 呼叫工具、取得 tool\_result、再把結果送回上下文。
