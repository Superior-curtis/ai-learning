## 上下文系統：Git、CLAUDE.md 與系統提示詞注入

Claude Code 給人的一個強烈印象是：它不像在面對一段孤立程式碼，而像在理解整個專案。

這背後最關鍵的原因之一，就是**上下文系統**。

Git 狀態
分支/提交/髒狀態CLAUDE.md
專案規範記憶檔案
可注入知識日期/環境
系統背景⬇context.ts → 統一整理 → 注入模型

***

### getSystemContext()：補充系統級背景

從原始碼看，`getSystemContext()` 至少會處理一類非常重要的資訊：**Git 狀態**。

它會主動並行收集：

#### 這帶來的直接好處

髒狀態感知
模型知道當前工作區是否乾淨分支感知
模型知道你在哪條分支上變更方向
模型知道近期程式碼變化走向

***

### getUserContext()：補充使用者與專案約束

另一個重點是 `getUserContext()`。這裡會處理 **CLAUDE.md** 等記憶檔案，並注入當前日期。

CLAUDE.md 的意義非常大——你可以把它理解為**專案級工作說明書**：

📐
編碼規範📁
目錄結構約束🔧
特殊命令🚫
避免的操作

***

### 互動練習：這些資訊來自哪個管道？

來源
原因當前分支名稱

***

### 這不是單純「拼 prompt」，而是上下文治理

表面上看，這像在往系統提示詞裡加文字。但從工程角度看，本質更接近**上下文治理**：

什麼資訊值得長期注入？
Git 狀態、專案規範是每次任務都需要的高信號資訊什麼資訊要快取？
CLAUDE.md 讀取後快取起來，避免每次重讀什麼資訊在 bare mode 下跳過？
沒有設定檔案的專案不強制注入什麼資訊需要控制長度？
Git log 只取 5 筆，記憶檔案有過濾機制

***

### Cache Breaker 機制

這看起來簡單，但很能說明思路：上下文不是散落在系統裡的臨時字串，而是**被統一整理成結構化物件**，再交給後續主循環使用。

***

### 這層設計帶來的直接結果

有了上下文系統，Claude Code 在許多場景下會表現得更像「進入專案現場」：

📋
遵守倉庫約定
更容易維持一致性⚡
避免狀態衝突
感知髒狀態避免中斷🎯
理解任務脈絡
知道為什麼要這麼做

***

### 這層機制也有明顯邊界

⚠
注入內容長度有限，無法塞入整個專案⚠
Git 狀態是快照，不會自動即時刷新⚠
記憶檔案品質決定了部分行為上限關鍵結論： 上下文系統是增強器，不是萬能鑰匙。

***

### 一句話總結

> AI 程式設計工具之所以強，往往不是因為模型憑空更聰明，而是因為系統在模型開口前，就已經把「該知道的專案背景」準備好了。
