## Plan Mode 在架構裡的位置：不只是模式切換

很多人會把 Plan Mode 理解成「先寫計劃、不直接寫程式碼」的產品功能。但從原始碼看，它遠不只是一個 UI 狀態，而是貫穿**工具系統、權限系統、會話狀態、審批流程**的一套架構能力。

***

### 在工具層的明確存在

在 `tools.ts` 裡，Plan Mode 不是神祕隱藏能力，而是明確的工具：

Plan Mode 的進入和退出，都是系統正式建模過的**操作**，而不是臨時插進去的布林開關。

***

### Plan Mode 生命週期

🟢 預設模式EnterPlanModeTool
進入規劃⬇🟡 Plan Mode
產生計劃，等待審批使用者批准 → ExitPlanModeV2Tool拒絕 → 繼續修改計劃⬇🟢 恢復實現模式 → 開始編碼

***

### ExitPlanModeV2Tool 的關鍵定義

這段程式碼非常重要，因為它說明：

🔧
正式工具呼叫
退出 Plan Mode 是系統級操作🛂
預設要求互動
使用者必須確認👥
Teammate 行為不同
子 Agent 可自動退出

***

### 為什麼它和權限系統綁得這麼緊？

Plan Mode 的退出**不是模型自己說了算**——它是一個需要系統權限流程承認的動作。

***

### prePlanMode：狀態層的語義設計

在權限上下文中能看到 `prePlanMode` 這樣的欄位，說明系統會記住進入 Plan Mode 前的權限狀態：

進入 Plan Mode 前的權限狀態⬇prePlanMode 暫存⬇Plan Mode 審批階段⬇ 批准退出恢復到原本模式

Plan Mode 不是孤立狀態，而是對**整個權限語義有影響**。

***

### 為什麼要做到這個程度？

💡因為工程任務裡最危險的，不是「模型不會寫」，而是「模型太快開始寫」。Plan Mode 本質上是在系統層引入一個暫停點：
先整理方案 → 給人審核 → 審核通過後再進入執行

***

### 多 Agent 場景下更關鍵

🧑 主執行緒
Plan Mode = 使用者審批點🤖 子 Agent
Plan Mode = 團隊領導審批點

***

### 一句話總結

> Plan Mode 更準確的定位是：Claude Code 在自動化執行鏈路中**人為插入的一個「計劃審批閘門」**，透過工具、權限和狀態系統協同工作，確保從規劃到實現的切換是可控的。
