# 多代理系統安全：當 AI 能動手做事

> 📅 2026-08-04 · 深入研究
> 當代理會呼叫工具、瀏覽網頁、操作真實系統時，注入的影響從『說錯話』升級成『做錯事』。這篇談工具權限邊界、人在迴路，以及 MCP 工具的最小權限。

---

到目前為止的安全討論，都還停留在「模型會說錯話」的層次。`security-06-guardrails` 教你讓單一模型在單次推論裡不失控。但當你給模型**手**——工具、瀏覽器、真實系統的存取權——事情的性質就變了。

一個會呼叫工具的代理（`agents-01-what-is-agent`）不再是「回答你的問題」，而是「替你做事」。而 `security-01-prompt-injection` 告訴過你：模型無法可靠分辨指令與資料。把這兩件事擺在一起，會得到一個不安的結論——**只要代理會動手，注入就能變成未授權的動作。**

這篇談的就是這層新增的攻擊面：資料怎麼流進動作、工具權限的邊界在哪裡、為什麼高風險動作需要人在迴路，以及 MCP 工具的最小權限。

## 從「會說話」到「會做事」：攻擊面升級

先看攻擊面怎麼變大的。代理系統會把各種**不可信內容**讀進上下文：網頁、RAG 文件、電子郵件、工具回傳的 JSON、另一個代理的輸出（見 `agents-02-orchestration`）。在「只會說話」的模型裡，這些內容最多影響回答。但在代理裡，**上下文裡的文字可以直接變成工具呼叫的參數。**

```attack-surface
只會說話： 網頁內容 ─→ 影響「回答」
會呼叫工具：網頁內容 ─→ 影響「動作」

不可信內容（網頁 / 文件 / 工具輸出 / 子代理輸出）
      ↓
 進入上下文
      ↓
 被轉成工具呼叫參數（寄信、寫庫、改設定……）
```

這正是間接注入在代理場景的升級：`security-01-prompt-injection` 裡「轉寄郵件」的假想，在這裡是每天都可能發生的真實路徑。所以代理安全的第一課是：**把每一條「資料 → 動作」的路徑都當成潛在的授權邊界來設計，而不是假設模型會判斷來源。**

## 資料流進動作：讓工具呼叫穿過檢查點

既然不可信內容可能被轉成工具參數，防禦就該落在「工具呼叫」這個樞紐上——在參數真正生效之前，加上不依賴模型的硬檢查：

* **白名單**：只有明確允許的工具可以被呼叫，其他一律拒絕。
* **參數 schema 驗證**：每個工具定義參數的型別與範圍，不符合就攔下。
* **資料流標記**：當參數來自不可信來源（網頁、文件、外部 API 輸出）時，標記為「未驗證」，提高觸發人工審核的機率。
* **敏感動作攔截**：對寄信、刪除、轉帳這類參數做模式掃描，先攔後問。

```python
def authorize_tool_call(tool: str, args: dict, source: str) -> Action:
    if tool not in TOOL_ALLOWLIST:
        raise PermissionError(f"工具不在白名單：{tool}")
    validated = TOOL_SCHEMAS[tool].validate(args)
    if source == "untrusted" and tool in SENSITIVE_TOOLS:
        return Action.NEEDS_HUMAN   # 不可信來源 + 敏感工具 → 人在迴路
    return Action.EXECUTE
```

關鍵在「來源感知」：**同一個工具，參數來自使用者本人 vs. 來自網頁內容，風險完全不同。** 把來源標記帶進授權決策，是代理特有的護欄，傳統後端沒有這個概念。

## 工具權限的邊界

代理有越多工具，每個工具就像多一扇窗。權限設計的幾條鐵律，與 `security-04-secure-apps` 一致，但代理場景要更嚴格：

* **最小工具集合**：只暴露目前任務需要的工具。能讀就別給寫，能列就別給刪。
* **權限綁定目前使用者**：代理以「目前使用者」的身份做事，而不是以一個萬能的服務帳號。
* **以唯讀為預設**：除非任務明確需要寫入，否則給唯讀存取。
* **限縮資料範圍**：即使能查詢，也限制在該使用者自己的資料範圍內。

| 設計決策 | 高風險 | 低風險 |
|---|---|---|
| 工具暴露 | 給整個工具庫 | 只給任務需要的幾個 |
| 資料庫角色 | 管理員帳號 | 唯讀、限縮範圍的角色 |
| 寫入動作 | 自動執行 | 需確認或人在迴路 |
| 帳號身份 | 共用服務帳號 | 綁定目前使用者 |

## 高風險動作：人在迴路

再好的檢查也可能漏。最後的保險，是讓**高風險動作停下來等人**——human-in-the-loop。判斷「要不要等人」，看三件事：

1. **不可逆**：刪除、覆寫、寄出、轉帳——做錯了不能還原的動作。
2. **影響範圍大**：影響到其他使用者或系統層級的動作。
3. **來源不可信**：參數來自網頁、文件或外部工具輸出。

只要命中其中一項，就先暫停、展示「將要執行的動作與參數」，等使用者確認後才執行。這不是犧牲效率——它是把「代理做了不該做的事」的機率，從「靠模型判斷」換成「靠人拍板」。

> 代理安全的第一原則是：不要把「決定該不該做」完全交給模型。 模型是在同一串 token 上逐詞預測的統計系統（llmcore-01-next-token），它無法可靠分辨「這條指令來自系統」還是「來自一張網頁」。所以權限與審批必須由模型之外的程式把關：白名單、參數驗證、來源標記，以及高風險動作的人類確認。

## MCP 工具的最小權限

當代理透過 MCP 接上工具（`agents-03-mcp`），上述原則要落實在**每個 MCP server 的權限設定**上。MCP 讓你把外部工具接進代理，但也等於把攻擊面外包給了那些工具的實作——所以權限要在接入的那一刻就設好：

* **逐工具授權**：MCP server 可能暴露很多工具，只開放目前真正要用的那幾個，而不是全開。
* **最小範圍的憑證**：每個 server 用自己的、限縮權限的認證，而不是共用的萬能金鑰。
* **資料範圍限制**：server 能觸及的資料，限制在該使用者或該任務的範圍內。
* **敏感工具標記**：把「會寫入、會外送、會刪除」的工具標記為高風險，觸發人在迴路。
* **審計與監控**：記錄每個工具呼叫的參數與來源，出事時可以追溯。

如果你自己寫 MCP server，`mcp-03-build-your-own` 會帶你把工具的輸入與權限設計到位——安全要在你暴露工具的那一刻就內建，而不是事後補。

## 子代理的信任：別讓下游被上游帶走

多代理系統還有一層獨特的攻擊面：**代理之間的信任關係**。當主代理把任務交給子代理（見 `agents-02-orchestration`），子代理的輸出會回到主代理的上下文——而子代理讀過的內容，可能把它帶偏。

* **把子代理輸出當不可信內容**：子代理的輸出跟網頁一樣，是「資料」，不是「系統回報」。進入主代理前，照樣走內容隔離與標記（見 `security-06-guardrails`）。
* **不給子代理繼承的全權**：子代理拿到的工具與權限，應該比主代理更窄，而不是一樣或更寬。
* **限制子代理能做的事**：子代理的任務越專一，它被誘導後能造成的破壞越小——這本身就是一種最小權限。

一句話：**多代理只是把「資料 → 動作」的路徑變多，而不是變安全。** 每一條跨代理的路徑，都還是要穿過同樣的檢查點。

## 事件之後：從稽核日誌還原

就算所有防護都到位，仍要預設「會出事」。發生疑似事件的標準動作：

1. **止血**：關閉受影響的工具權限、暫停代理、回滾有問題的設定。
2. **取證**：從稽核日誌還原「哪一條資料 → 哪一個動作」——來源標記與工具呼叫記錄在這裡是命脈。
3. **補測試**：把這次的手法寫進自動化測試集，別讓它回來。
4. **復盤**：是哪一道檢查沒攔住？白名單、參數驗證、來源標記，還是人在迴路？

關鍵認知：**稽核日誌不是事後的裝飾，它是事件應變的地圖。** 沒有記錄，就沒有還原，也就沒有「下次不再犯」。

## 把安全設計進代理架構

最後，把這幾道關放到一起，看一個安全的代理流水線：

```text
不可信內容 → [內容隔離] → 上下文
↓
使用者指令 → [輸入過濾] → 代理 → 工具呼叫
↓
[授權檢查：白名單 + 參數 + 來源]
↓
高風險？──是──→ [人在迴路：等確認]
↓否
[稽核日誌] → 外部世界
```

每一段「資料 → 動作」的路徑，都至少穿過一層不依賴模型的檢查。這不是要你放棄自動化——而是要你**只讓安全的動作自動化**。真正需要人工的，永遠是那些不可逆、影響大、或來源不可信的動作。

## 一句話總結

> 多代理系統安全，不是「讓代理更聽話」，而是**在『資料』通往『動作』的每一條路上，都設下由程式而非模型把關的檢查——白名單、參數驗證、來源標記、最小權限，以及高風險動作的人類確認**。模型的聰明負責做對的事，框架的規則負責攔下不該做的事。

#### Q: 為什麼同一個工具呼叫，來自『使用者本人』與來自『網頁內容』需要差別對待？

* 因為網頁內容的參數格式跟使用者輸入不同，需要先轉檔

* 因為兩者的信任程度不同：後者可能是攻擊者藏進不可信內容的誘導，觸發動作前需要更高門檻的檢查

* 因為使用者本人輸入更快，可以跳過所有檢查

* 因為網頁內容不能當工具參數，只能當純文字參考

> 💡 代理會把不可信內容（網頁、文件、工具輸出）讀進上下文，這些文字可能被轉成工具參數。來自使用者本人的指令有一定的信任基礎，來自網頁等不可信來源的參數則可能是誘導。所以用『來源標記』把兩者分開，對不可信來源的敏感動作提高門檻、或觸發人在迴路，是代理安全的核心手法。
